## 已确认开发习惯

- 按完整业务闭环组织改动和提交：巡检、物资、异常上报、工单、审核须同步核对前后端字段、权限和状态机。
- 优先最小、可验证改动；不借修复之机重构相邻模块。每项改动先明确假设、成功条件和回归范围。
- 后端以 `backend/app.py` 为主，少量独立 blueprint 位于 `telemetry.py` 和 `operations_baseline.py`。SQLite 多表写操作必须显式 `commit()`；迁移采用幂等函数，在 `init_db()` 中执行。
- Web 固定 React + Ant Design，按页面组件组织，接口集中在 `react-vite/src/services/api.js`；小程序固定微信原生页面、WXML/WXSS 和 `services/api.js`，不引入新的 UI 框架。
- UI 统一使用既有 design token、枚举中文映射和紧凑运营台布局。Web 页面改动必须通过 `python check_ui_zh.py`，不允许可见英文、裸枚举或默认英文确认按钮。
- 关键业务规则优先补 Python `unittest`；小程序纯状态逻辑使用 Node 内置断言。Web 改动至少执行 `npm run build`，涉及 UI 时还要检查实际渲染。
- 不混入数据库、上传文件、截图、构建产物或不相关整理；提交前检查 `git diff --check`、目标测试和构建结果。

## 当前切入点

当前最高优先级是落实使用反馈 `FB-003` 已确认的展示边界，而不是修改接口：

- `user_sites` 表示该运维人员负责哪些站点。
- 首页 `GET /api/mobile/my-today` 和现场页 `GET /api/mobile/today-execution` 只展示已审批、已生成且分派给当前账号的执行包。
- 因此“负责站点 10 个”与“今日待检 0 个”在当前实现中可以同时成立。

已确认采用计划驱动：无执行包时不允许填写巡检，仅在首页、现场页明确显示负责站点和“今日无任务”。负责站点列表只读，不复用巡检入口、不新增写入接口，避免绕过排程、审批、资源确认和审计链路。该本地改动待在微信开发者工具中按无任务账号完成验收。

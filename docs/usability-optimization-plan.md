# 水质智慧运维系统 · 可用性优化方案

> 生成日期：2026-07-30
> 背景：系统功能 + 冒烟测试已通过，但"可用性"薄弱。本文把"可用性"拆成两层——
> - **UX 易用性**：一线/管理者能否顺畅、少步数、低误操作地完成真实作业；
> - **系统可用性(Availability)**：真实环境（弱网/并发/异常）下能否稳定、可观测、可恢复。
> 两层都弱，根因不同，分别治。

---

## 0. 诊断：AI 开发系统的可用性薄弱根因

| # | 根因 | 本项目证据 |
|---|------|-----------|
| 1 | 目标错位：以"功能通"替代"人好用" | 全系统以接口/单测验收，无 UX 度量 |
| 2 | 视觉与结构不一致 | 网页 13 页 A–I 不一致（`ui-structure-healthcheck-2026-07-25.md`）；小程序六页 A–H（`miniprogram-structure-baseline-2026-07-25.md`）；`pageStyles.js` 定义基准但 AlertsPage 未采用（根因 J） |
| 3 | 任务流非用户视角 | 巡检执行页未嵌试剂更换/设备异常/旧件回收；首页出发前"车辆/备件"只读不可操作；`spare_part_requests` 与 `parts_requests` 双表并存 |
| 4 | 缺四态与容错 | AI 少写加载/空/错误/弱网兜底，出错即白屏或堆栈 |
| 5 | 缺可观测与韧性 | 无监控/告警、Flask dev server（`app.run`）、无前端错误边界 |

---

## 1. 先定"怎样算可用"——度量指标（不量化就无从验收）

**UX 侧**
- 关键任务步数：高频动作（打卡/拍照/接单/异常上报）移动端 ≤ 2 触达，PC 端 ≤ 3–4 触达（既有《交互深度规范》）。
- 任务成功率 / 放弃率：抽样走查 5 条核心动线，目标成功率 ≥ 95%。
- 首屏与操作响应：列表/详情 ≤ 1s 可见，提交 ≤ 2s 反馈。
- 错误自愈率：操作失败后能凭界面提示自行恢复的比例。
- 满意度：一线 + 管理者小样本 NPS/问卷。

**系统侧**
- 接口 P95 耗时、错误率（4xx/5xx）。
- 崩溃/白屏率、弱网降级成功率。
- 监控覆盖率（关键接口/任务有日志+告警）。

> 已有基础可复用：`telemetry.py`（12 事件白名单）、`operations_baseline.py`。把 UX 指标接进这套埋点，而不是另起炉灶。

## 2. 优化方案（六层）

### 层一 · 一致性地基（复用已有计划，不必重做）
- 直接套用 `ui-unify-execution-plan.md` 批次 0→3（模板组件 `<ManagementPage>` + pageStyles 落地 → 工具栏 → 状态色 → Card/size/分页 → 操作列/ellipsis）。
- 小程序补全局组件：把"横向选择条 / 列表行 `.row` / 详情字段 `.d-*`"提进 `app.wxss`，六页改引用（对应 `miniprogram-structure-baseline` 的 A–H）。
- **验收**：同层级页面视觉与结构一致，切换无"换 app"感。

### 层二 · 任务流与信息架构（可用性最大杠杆）
- 按角色重做 IA：
  - **移动端（一线主力）**：首页(待办聚合) → 巡检执行 → 工单处理 → 告警 → 我的。高频动作置顶、1–2 触达。
  - **网页端（管理者低频）**：围绕"审核中枢 `/audit` + 数据总览"组织，其余为二级入口。
- **把作业"编织进日常执行流"**（既有战略）：巡检执行页嵌入试剂更换+质控、设备异常主动上报、旧件回收；首页出发前卡做**可操作前置**（确认车辆 / 一键申领缺件）。
- **合并双备件表**为一套，下线孤儿表 `parts_inventory`，消除"两个申请入口"困惑。
- 每页补"你现在在哪 / 下一步做什么"上下文（阶段标识 + 角色标识）。
- **验收**：核心动线步数达标，无"同一个事两个入口"。

### 层三 · 四态与反馈（补 AI 最易漏的）
- 统一 **加载 / 空 / 错误 / 成功** 四态组件（Web 用 antd `Spin/Empty/Result/message`；小程序用统一 `loading/empty/error` 模板）。
- 操作确认 + 撤销 + 防重复提交（提交中禁用按钮、乐观更新+回滚）。
- 友好错误：给"原因 + 下一步"，**绝不抛堆栈/英文**。
- 弱网与离线：巡检已离线优先（#314），其余模块至少做到"失败可重试、不丢本地输入"。
- **验收**：任意失败路径都有可恢复界面，无白屏。

### 层四 · 移动端现场适配（一线真战场）
- 触控目标 ≥ 88rpx、字号/对比度达标、主操作单手可达。
- 户外/弱光可读（已定 Design Token：背景 `#F5F6F8`、主色 `#0D9488`）。
- 关键操作防误触（如"提交工单""回收设备"加二次确认 + 滑开）。
- **验收**：一线在户外单手完成高频动作，误触率下降。

### 层五 · 引导与赋能
- 首次进入引导（3–5 步）；关键流程悬浮 tip。
- 字段级说明：试剂/设备参数多，加 hover/问号解释，降低培训成本。
- 帮助入口常驻（网页端右上、小程序"我的"内）。
- **验收**：新人不看文档能完成首次巡检。

### 层六 · 系统可用性(Availability) 韧性
- 前端全局错误边界 + 统一异常捕获上报（接 `telemetry`）。
- 后端：Flask dev server 换 **gunicorn**；compose 加 `healthcheck` 探 `/api/health`。
- 可观测：结构化日志 + 轮转；uptime 监控 + 关键任务告警（见 `pre-launch-checklist.md` 第 13–16 条）。
- 性能：列表大数据量评估虚拟滚动；接口耗时纳入基线。
- 部署韧性：镜像/DB/上传卷备份 + 回滚（同上文档）。
- **验收**：单点故障可恢复，异常有告警，无静默失败。

## 3. 优先级路线图

| 优先级 | 内容 | 依赖 | 预期收益 |
|--------|------|------|----------|
| **P0** | 层一 一致性地基 | 已有计划 | 消除"换 app"感，降认知负荷 |
| **P1** | 层二 任务流审计 + 高频动线 + 合并双备件表 | P0 后 | 可用性最大杠杆，步数达标 |
| **P2** | 层三 四态 + 反馈 + 容错 | 独立可做 | 去白屏，错误可恢复 |
| **P3** | 层四 移动端适配 + 层五 引导 | P1 后 | 一线真机好用、易上手 |
| **P4** | 层六 可观测 + 韧性 | 部署就绪后 | 真实环境稳、可恢复 |

> 执行注意：阶段二 UI 统一化已由另一 agent 在 git 上推进，本层一/层二与其重叠——**施工须走同一 git 协调，避免冲突**。本方案仅规划，不自行改码。

## 4. 建议的下一步（可任选，我可立即展开）

1. **任务流走查表**：产出"角色 × 核心任务 × 当前步数 × 目标步数 × 断点"矩阵（P1 的输入）。
2. **四态审计**：对 13 网页 + 6 小程序页扫一遍加载/空/错误/成功态覆盖，出缺口清单（层三输入）。
3. **直接施工层一**：按 `ui-unify-execution-plan` 批次 0→3 落地一致性（需协调阶段二 agent）。
4. **UX 度量埋点**：在 `telemetry` 基础上加"任务开始/完成/放弃/错误"事件，先有数再优化。

建议从 **#1 任务流走查** 起步——它是 P1 的地基，也能最快暴露"AI 觉得通、人觉得绕"的地方。

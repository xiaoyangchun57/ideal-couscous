## 2. 已确认的度量范围

### 已采集

- 一线：到站打开、签到、拍照、离线暂存与同步。
- 管理端：审核打开/提交、评估报表打开/导出、行动队列深链进入。

### 当前展示规则

- 审核耗时：仅同一 `review_id` 的打开和提交事件配对后计算中位耗时。
- 报表自助率：`report.exported / report.opened`；打开样本为 0 时必须显示“采集中”。
- 行动队列：目前仅是进入次数样本，不得命名为“决策率”或用于管理评价。
- 任何指标未满真实基线观察期（建议 2–4 周）前，不设目标、排名或奖惩阈值。

## 3. 已完成保障层：影像抽样审核

目标是“审核员只关注可疑照片，正常照片可批量通过”，但绝不能因为批量操作越权或误放行。

### 已完成

1. `auto-review` 按当前审核人的站点权限过滤；越权站点请求返回 403。
2. 前端先请求预览，再展示“正常照片数量 / 标红保留数量”的确认框。
3. 自动通过写入审核人、审核时间与 `review_action='auto_pass_normal'`。
4. 站点照片、巡检照片、工单照片的定位与拍摄时间传递已核查；缺失元数据的非工单照片不参与自动通过。
5. `reevaluate` 仍仅管理员可执行，且不会在启动时自动回填。
6. 接口测试已改为临时 SQLite 与 Flask 测试客户端，不再触碰运行数据库。

### 后续低优先级完善

1. 将标红规则从 `app.py` 抽为独立、可单测的模块；`app.py` 仅负责注册接口与调用。
2. 审核页按“标红优先 / 全部待审”提供筛选；批量操作只对当前可见且有权限的正常照片生效。
3. 对 GPS 偏离、未来时间、异常巡检项各自记录规则命中；支持多规则同时命中。
4. 增加审核质量看板：标红数量、自动通过数量、人工驳回数量，只展示样本量，不评价人员。

### 验收

- 普通审核员无法批量通过其他站点照片。
- GPS 偏离、未来时间、关联异常项三类照片均置顶并保留人工审核。
- 正常照片批量通过后可追溯到操作人和操作来源。
- 自动化测试不触碰 `data/water.db`；后端单测、接口测试、前端构建全部通过。

## 5. 已确认主路线：主动运维

被动层保持静态可用，但停止新检测、SPC、SLA 或真实数据接入开发。按以下顺序启动独立设计和实施：

1. **巡检深化**：以“运维自排 → 管理员审批”为主链。自动排程只能生成待确认草案与风险/加派建议，不得绕过人工确认直接派发；三代计划体系仅在移动端回归清单通过后收口到 v2。
2. **物资编织进执行流**：先实现出发前车辆/备件确认、现场试剂更换与质控、主动设备异常上报/旧件回收；不新建独立“物资中心”。车辆充电、月度车况、维修等拆为后续车辆子阶段，避免扩大本阶段。
3. **备件单据收口**：以 `parts_requests`（v2）作为统一目标模型，移动端逐步迁移接入；`spare_part_requests` 保留只读历史，迁移验证完成前不删除旧数据。
4. **移动端异常上报**：GPS、照片、异常编码 → 管理端核实/归档 → 派生工单可视化闭环。

### 5.1 巡检深化：第一实施切片（进行中）

已落实“到期检查项只形成排程建议”的安全边界：

1. 新增纯计算模块，按 **责任运维人员 × 周/月/季/年频次 × 当前周期** 汇总 `inspection_schedules` 的到期项；站点归属只认 `user_sites`。
2. 新增 `GET/POST /api/plan-schedules/draft-recommendations`：先展示候选，人工点击后才创建 `plan_schedules.status='draft'`。
3. 创建草稿不调用任务生成、车辆锁定、备件预留/扣减或审批；候选失效、已有草稿都会阻止重复创建。
4. PC 的“巡检计划调度”页已展示到期建议并提供“生成待确认草稿”入口。草稿仍须由运维人员完善排程和资源后提交，再由管理者审批。

已实施：每天 06:05 的草稿生成任务。它只调用同一候选计算并创建可编辑草稿，重复运行保持幂等；不生成执行包、不提交/审批、不锁车、不预留或扣减物资。

已实施：排程建议把未归档的人工异常上报作为独立风险信号（不因已派生工单而隐藏），在排程和审批时提示现场复查并参与站点优先级评分；普通运维人员的建议查询严格限制在本人负责站点。

永不实施：自动提交、自动审批、自动派发。任何“自动”能力只允许提醒或创建可见候选/草稿，永远不得越过人工确认。

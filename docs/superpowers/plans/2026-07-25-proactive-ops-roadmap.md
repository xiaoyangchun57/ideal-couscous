## 一、战略转向说明

### 原权重
被动响应式（数据监控触发）占主导：管道异常检测 → L1/L2/L3 审核 → 自动派单 → SLA 升级 → 告警↔审核↔工单闭环。该体系代码已完整，但**强依赖真实数据源接入**。

### 瓶颈（已确认不可短期解决）
真实数据接入（SL651 国家水站协议 / 实时写入路径）当前无法打通：
- `generate_sensor_data` 仿真器已关闭（静态演示模式，`app.py:15696`）
- SL651 接收器默认不启动，需 `ENABLE_SL651=1`（`app.py:15715`）
- 被动层调度任务（auto_data_review 每 10min / alert_escalation 每 5min）仍在跑，但喂入的是静态/种子数据

→ 继续投入被动层开发，边际价值趋近于零。

### 新权重
**人主动发起的运维动作优先**：巡检、物资管理、异常上报。被动层保持静态运行、停止新开发。

---

## 二、被动层处理决议（用户拍板）

| 项 | 决议 |
|---|---|
| 静态运行 | **保持**：现有被动层在静态/种子数据上正常运行，不影响一线 |
| 新功能开发 | **停止**：不接真实数据、不接 SPC 动态阈值、不新增任何被动检测/审核/SLA 功能 |
| 孤儿表 `threshold_rules.rule_type='spc'` | **留待未来**：真实数据接入时优先将其接入 `detect_site_anomalies`/`auto_data_review`，禁止重建一套阈值机制 |
| 现有被动 UI | **不隐藏**：告警页、数据审核 Tab、审核中枢等照常可用（功能正常） |

**不做清单**：不接真实数据源 / 不新建被动功能 / 不重建 SPC 阈值 / 不隐藏被动 UI。

## 三、三模块现状与缺口（证据化，来自只读调研）

### 巡检（最成熟，三代并存）
- ✅ 已建：`insp_plans`/`insp_plan_items` + `inspection_templates`/`inspection_configs`/`inspection_schedules` + 顶层 `plan_schedules`（三层：调度审批→计划→检查项）；计划生成(周/月/季/年)、任务按 `user_sites` 分配、移动端签到(500m GPS 围栏)/照片/审核闭环均 built。
- ❌ 缺口：①**无自动排程**（生成靠人工点 smart-preview/confirm，调度器无定期生成任务）；②频度驱动非风险/条件驱动；③巡检异常只转工单、**不回灌生成新计划**（闭环半截）；④**三代并存**（v1 `inspection_plans`/0行 + `weekly_inspection_plans`/5行 + v2），Web 入口分散在 `MaintenancePage` 与 `PlanSchedulesPage`，`App.jsx:56` 仍有停用残留注释。

### 物资管理（能力已散布存在，真问题是"松散、未嵌入日常"）
- ✅ 已散布存在（非缺失）：仪器/设备台账、备品备件库存与申领/回收、试剂库存与质控、车辆与用车——这些管理能力在代码里都有落点（设备台账页、试剂管理、备件 API、用车审批等），只是分散在各处、彼此无衔接。
- ❌ 真问题（用户纠偏 2026-07-25）：①各处管理松散、与巡检/工单实际作业**脱节**；②一线（移动端主力）在日常「边做边管」时不顺手——出发前确认车辆/备件、巡检中记试剂更换+质控、发现设备异常→上报/回收，这些动作目前没顺滑嵌进执行流；③双套备件申请表(`spare_part_requests` v1 vs `parts_requests` v2)技术债；④盘点(P2)、备件维修/报废/外部采购(P3)仍缺失；⑤活跃度低（inventory_logs=2、spare_part_requests=3、parts_requests=5），多数流程未演练。

### 异常上报（已建独立模块，欠可见性）
- ✅ 已建：`manual_reports` 表（report_type: sensory/equipment/environment/violation/pollution）+ `anomaly_codes`(7条) + `GET/POST /api/manual-reports`；与告警(`flow_type='manual'`)和工单(`source='manual_report'`)通过字段**明确解耦**；前端 `ReportsPage.jsx` 存在，导航「异常上报」(`navigation.jsx:35`)。
- ❌ 缺口：①小程序**无独立 reports 页**（可能内嵌）；②无专属「上报→核实→归档」可视化看板（目前并入工单/告警流）；③演练数据极少（manual_reports=1）。

## 四、重新加权路线图（优先级：巡检 → 物资 → 异常上报）

### 阶段一：巡检深化（当前最成熟，加"主动智能"）
1. **自动排程**：新增 cron 任务，按 `plan_schedules.next_due_date` 自动触发 smart-preview→confirm 生成下期计划。锚点：`v2_generate_plans`(`app.py:7228`)、`smart-preview`(`7350`)、`confirm`(`7465`)、调度器注册(`app.py:15703`)。
2. **风险/条件驱动加派**：把 `manual_reports` / `alerts`(flow_type='manual' 或低风险) 作为加派信号，注入计划生成——打通"被动产生的事件喂入周计划智能建议"这一已知缺口（记忆：被动层唯一真缺口=衔接层）。
3. **异常回灌**：巡检异常项(auto-generated 工单) 闭环后，若属系统性问题，自动建议生成针对性复查计划，闭合半截闭环。
4. **三代整合（谨慎）**：写入统一到 v2，停用 v1(0行)/weekly(5行) 的新增入口；移动端 `inspection.js:51` 已绑 v2，整合须回归移动端。
5. **Web 入口收口**：`MaintenancePage`(计划管理) 与 `PlanSchedulesPage`(调度审批) 明确层级，清理 `App.jsx:56` 停用残留。
- **验收**：cron 跑通自动出下期计划；手动上报后能见到加派/复查建议；三代只留 v2 且移动端回归 PASS。

### 阶段二：物资管理"编织进日常"（非新建中心，而是整合+嵌入）
> 前提（用户纠偏）：物资管理=巡检附带产生的管理环节（仪器/设备/备品备件/试剂/车辆），能力**已有**、无需另起炉灶。重点是收拢松散、嵌入一线日常执行流。

1. **先盘点动线**：梳理运维人员在一次完整巡检/工单里会碰到哪些物资动作（出发前确认车辆/备件 → 到站签到 → 试剂更换+质控 → 设备异常→上报/回收 → 离站），标出每步当前卡在哪、数据落在哪张表。
2. **嵌入移动端执行流**：把车辆/备件确认、试剂更换+质控、设备异常上报/回收等动作，做成巡检执行页(`pages/inspection`)与工单处理页内的顺手入口，让一线"边做边管"；落实业务规则"接单后、出发前确认备件/车辆"。
3. **收口松散管理**：把分散的设备/试剂/备件/车辆管理从各处归拢到统一、连贯的视图（复用现有台账页与审核中枢，**不新建"物资中心"独立页**），消除重复与脱节感。
4. **合并双套备件申请表**：`spare_part_requests`(v1) 与 `parts_requests`(v2) 统一为一套入口（保留历史数据，前端只暴露一个）。
5. **按需补齐缺失环节**：盘点(P2)、备件维修/报废/外部采购(P3)——按一线实际痛点补，不强行全做。
- **验收**：一线在移动端一次巡检/工单流程中，能顺手完成车辆/备件确认、试剂质控、设备异常上报/回收，无需跳转到松散独立页面；Web 侧管理视图连贯无重复。

### 阶段三：异常上报完善（已建80%，补可见性）
1. **小程序独立入口**：新增 `pages/reports`（或嵌入 site/alert 页），支持 GPS+照片+异常编码选择。
2. **专属看板**：`ReportsPage.jsx` 增强——按 report_type/status 筛选、上报→核实→归档可视化时间线、与派生工单/告警联动展示。
3. **演练数据**：填充多类型(sensory/equipment/environment/violation/pollution)种子，端到端验证。
- **验收**：移动端可上报→Web 看板可见→核实归档→派生工单闭环，全链路演练 PASS。

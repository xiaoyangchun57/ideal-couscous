# 水质智慧运维项目全生命周期产品复盘

> 复盘基线：2026-08-14
> 复盘对象：从原始需求、规划设计、开发、测试整改、发布与真实使用反馈倒推整个项目
> 用途：形成后续产品决策、开发协作和持续优化的长期参考，不作为当前版本发布验收结论

## 1. 复盘方法与证据边界

这不是一份功能总结，也不是为既有结果寻找合理性的项目总结。复盘回答六个问题：

1. 项目最初要解决的真实问题是什么；
2. 当时基于什么假设做了哪些设计；
3. 哪些设计创造了实际价值；
4. 哪些问题在开发和真实使用中反复出现；
5. 根因属于需求、产品、实现、测试还是协作；
6. 下一阶段应该继续什么、停止什么、验证什么。

本文使用三种证据等级：

- **事实**：可由原始需求、代码、Git、测试记录、真实 UI 记录或用户反馈直接确认。
- **推断**：由多项事实共同支持的产品判断，但不是当时参与者的原话。
- **假设**：未来方向或尚未经过真实业务数据验证的方案，必须在实施前再次验证。

重要限制：

- 当前 Git 可见历史始于 2026-07-23，但需求文档和开发日志可追溯到 7 月中旬，因此早期阶段以文档证据为主，不能把提交历史当作项目真正的起点。
- 7 月 30 日的“内部角色走查”明确是自动化内部测试，不是真实用户研究；其中的 40 项通过只能证明已登记问题被复测，不能证明产品整体可用。
- 8 月 12 日的 r5/r6 是历史冻结对象；2026-08-14 的开发工作树已有大量未提交修改，历史候选不能代表当前开发线。
- 原始《关键需求.docx》因本机缺少 LibreOffice 未完成整页视觉渲染；本文通过结构化 OOXML 读取正文和表格，并单独检查了其中的巡检照片要求图片。

## 2. 结论先行

这个项目真正要解决的，不是“做一个监测平台”，而是把分散在文字排程、人工沟通、现场拍照、车辆与物资申请、异常处理、审核和报表中的运维工作，变成一套**一线愿意用、管理者看得清、关键事实可追溯的线上闭环**。

项目已经完成了三个有价值的跨越：

1. 从单纯的数据监测扩展为计划、执行、工单、资源、证据、审核和管理监控的一体化系统；
2. 从只重功能结果逐步补上权限、事务、幂等、失败恢复、审计和真实 UI 验收；
3. 从“让用户理解系统状态”开始转向“系统承担技术判断，用户只处理业务责任”。

但项目的主要矛盾也很明确：**功能扩张速度长期快于业务口径、角色责任、现场习惯、异常恢复和真实用户验证的收敛速度。**

这导致后期大量时间不是花在创造新价值，而是花在统一同一个对象在不同页面、接口、角色和时间点上的含义。影像证据、签到、补拍、工单、巡检审核和版本冻结只是这种结构性问题最集中的表现。

下一阶段不应继续以功能数量和冻结版本数量衡量进展，而应转为：

- 核心任务是否在线完成；
- 用户是否少走步骤、少重复劳动；
- 失败后是否能自主恢复；
- 页面、接口、数据库、通知和审计是否表达同一事实；
- 真实现场使用是否优于原来的文字、电话和线下表格。

## 3. 项目诞生：原始问题不是“缺系统”，而是工作事实分散

### 3.1 原始业务证据

原始需求中已经出现了后来全部核心模块的雏形：

- 运维人员用文字向主管提交周计划；
- 用车要记录、审批并检查时间冲突；
- 不同站点、仪器和厂家对应不同试剂，需记录更换和剩余可用时间；
- 每个站点、检查项有不同照片数量和审核要求；
- 工单、巡检、校准、试剂配置、车辆里程、加油和养护都会产生影像；
- 数据健康度应按正常参数量与总参数量计算，而不是简单按在线站点计算；
- 运维人员与负责站点强关联，管理员、审核员和运维人员职责不同；
- 网页端负责管理、监控和审核，移动端负责定位、拍照、通知和现场执行。

这些需求共同指向四类原始问题：

| 原始问题 | 业务损失 | 产品应承担的责任 |
| --- | --- | --- |
| 工作安排分散在文字和口头沟通中 | 计划、车辆、备件和执行无法联动 | 建立可执行、可调整、可追溯的计划与资源链路 |
| 现场事实依赖照片和人工描述 | 审核难、归档乱、真实性难判断 | 保留可信来源和业务归属，让审核只判断业务内容 |
| 每个模块各自记录状态 | 同一件事在计划、工单、通知和统计中互相矛盾 | 建立业务对象、责任人、状态和时间的统一权威源 |
| 管理者看见很多数据但难以行动 | 监控不能转化为安排、审核和处置 | 以待办、异常和进度为中心组织管理端 |

### 3.2 早期就存在的产品风险

原始需求广度很大，几乎覆盖完整运维体系，但没有先形成以下基础产物：

- 按角色排序的前三项关键任务；
- 现场一天的真实行为观察；
- 当前线下流程、耗时和失败点基线；
- 核心对象及其责任边界；
- “本期不做什么”的清晰范围；
- 功能上线后用什么指标证明减少了负担。

**推断：** 项目从诞生起就具有强烈的“全域数字化”诉求，却缺少同等强度的优先级和验证机制。这为后续按数据实体快速铺页面、每发现一个对象就增加一个模块创造了条件。

## 5. 产品架构是如何演化的

### 5.1 从实体页面到三层业务结构

早期系统主要按实体组织：站点、设备、试剂、车辆、工单、告警、影像和审核分别成为页面。这样开发直接，但用户需要自行在页面之间拼接一项工作。

7 月 21-22 日的规划开始形成更合理的三层结构：

1. **调度层**：计划、车辆、备件、风险提示和审批；
2. **执行层**：到站、检查、处理、拍照、工单和提交；
3. **审核与管理层**：内容审核、异常处置、进度监控、档案和报表。

这个方向是正确的，但还需要一个贯穿三层的“事实层”：

- 谁是当前责任人；
- 对哪个站点、计划、检查项或工单负责；
- 当前业务状态是什么；
- 哪些时间是业务时间、拍摄时间、上传时间和审核时间；
- 哪些证据当前有效，哪些只是历史；
- 失败后恢复动作是什么。

后期大部分跨模块缺陷，实质都是事实层没有在一开始成为统一产品模型。

### 5.2 双端职责演化

目前合理的双端职责应为：

- **小程序**：今天做什么、到站、现场查看、拍照、检查、工单处置、异常上报、补拍和消息；
- **Web**：全局查询、监控、资源协调、审核、异常处置、档案追溯、人员权限和报表；
- **后端**：权限、站点范围、状态迁移、来源可信、幂等、事务、审计和统计口径的最终权威。

过去的偏差包括：

- 把管理配置暴露给不需要的角色；
- 让审核员理解照片技术资格；
- 在 Web 和小程序分别推断同一状态；
- 把前端按钮隐藏误认为权限；
- 让客户端上报数量、来源、位置或状态作为业务事实。

双端不是“功能复制”，而是同一业务事实面向不同责任人的不同操作窗口。

## 6. 八个关键产品决策的复盘

### 6.1 “周计划是发令枪”

**价值：** 把文字排程、车辆、备件、审批和任务生成串成闭环，解决计划与执行脱节。

**偏差：** 如果把所有现场事务都强行纳入计划，临时告警、独立工单和突发处置会被迫绕路。

**更新后的原则：** 计划是计划性工作的主入口，不是所有工作的唯一入口。临时工单和告警可直接进入现场执行，但必须共享站点、责任、资源和审计规则。

### 6.2 “站点是执行锚点”

**价值：** 设备、试剂、巡检、工单和数据天然围绕站点聚合，减少跨页面查找。

**偏差：** 站点关联不能替代业务对象关联。照片仅关联站点而不关联检查项或工单，会导致审核归属和有效数量无法判断。

**更新后的原则：** 站点提供空间上下文，检查项和工单提供业务责任，两者都必须存在。

### 6.3 “打卡后才能拍照”

**价值：** 建立现场来源可信基础，防止异地旧图直接成为正式证据。

**偏差：** 现场人员常先集中拍摄一批照片，再逐项处理，最后补拍结果；强制每张照片在特定检查项步骤中即时产生会违背工作习惯。审核也可能在离站前或离站后完成。

**更新后的原则：** 不强制“处理前/处理中/处理后”状态机。到站后的可信拍摄可以先形成现场照片，再由用户低成本关联业务项；返场补拍只重开被驳回业务项，不重建整站签到。

### 6.4 “影像审核重在真实性”

**价值：** 时间、位置、来源和重复校验确实是证据可信的基础。

**偏差：** 把 qualification、依据、人工核录、整改等技术状态暴露给审核员，等于把系统的不确定性转嫁给人。

**更新后的原则：** 系统判断来源是否能作为正式证据；审核员只判断照片内容是否满足检查项或工单要求。来源不合格的材料可以保留，但不进入主审核、不计数，用户只看到可执行的“需要现场重拍”。

### 6.5 “影像统一审核”

**价值：** 管理者需要统一的待办入口和一致操作体验。

**偏差：** “统一入口”不等于“统一业务口径”。巡检照片、工单照片和无归属站点影像的责任与通过后结果不同。

**更新后的原则：** 统一审核提供一个入口，但按业务对象归口：巡检照片进入巡检质控，工单照片进入工单审核；无业务归属材料不制造主审核任务。

### 6.6 “异常驱动、正常批量通过”

**价值：** 降低审核员逐张点击的机械负担。

**风险：** 系统只能可靠判断来源和部分图像质量，不能在没有验证准确率的情况下替审核员判断业务内容正常。

**更新后的原则：** 来源失败在审核前拦截；内容审核可以按检查项批量操作和默认聚焦异常，但是否自动通过必须由真实漏审率和责任制度证明，不能只因效率目标上线。

### 6.7 “权限隔离”

**价值：** 后期已从前端隐藏提升为服务端角色、站点、对象归属和事务内复核，并增加越权零副作用测试。

**教训：** 管理员、审核员和现场执行人是不同责任轴。管理员能管理不等于能代替现场人员生成证据；审核权也不等于资源和主数据管理权。

**更新后的原则：** 角色决定可做什么，站点与对象归属决定对什么做，当前状态决定现在能否做，三者缺一不可。

### 6.8 “严格冻结和版本追溯”

**价值：** 不移动标签、候选白名单、发布包校验和历史对象隔离能避免部署错版本。

**偏差：** 在产品口径仍变化时连续创建 r1-r6，把验证资源消耗在历史候选，而不是先收敛问题。

**更新后的原则：** 开发阶段只维护一个问题清单和当前工作树；需求闭环、定向测试和真实 UI 通过后，才为唯一候选执行一次全量门禁和冻结。

## 7. 做对了什么

1. **愿意承认产品方向错误。** 7 月 21 日已经明确记录“功能堆砌、自我感动、反向增负”，没有把所有问题归咎于用户不会用。
2. **没有为追求新技术重写系统。** 多次规划坚持在 React、Flask、SQLite和微信原生小程序上渐进改造，符合当前规模和交付阶段。
3. **逐步建立了安全和一致性底线。** 服务端权限、站点范围、事务重读、批量原子校验、幂等、不可变审计和零副作用测试已经成为明确规则。
4. **开始区分自动测试与真实 UI。** 后期能明确标注 `NOT RUN`，不再用单测或 API 结果冒充 Web、小程序和真机体验。
5. **真实反馈能改变产品方案。** 影像资格状态机、补拍责任、审核归口和水印相册定位要求都因真实使用被重新简化，而不是维护既有设计面子。
6. **上线工程基础明显加强。** HTTPS、反向代理、上传持久化、数据库备份、健康检查、回滚和生产域名被纳入发布门禁。

## 8. 主要失误及根因

### 8.1 把“功能通”当作“产品完成”

早期测试主要证明接口成功、页面渲染和正向状态流转。真实使用后来暴露的却是：提交失败无提示、筛选锁住页面、关注不持久、弹窗遮挡、图片破损、权限入口错误、状态互相矛盾。

**根因：** 完成定义围绕实现结果，而不是用户是否能独立完成、失败后能否恢复、跨端事实是否一致。

### 8.2 产品原则没有变成持续门禁

弱网、角色范围、异常驱动、站点中心、少步骤和真实数据在 7 月的文档中都出现过，但后续仍反复遗漏。

**根因：** 原则停留在文档，没有进入需求模板、任务交接、代码 Review、UI 验收和发布清单。

### 8.3 真实现场研究太晚

7 月 21 日已建议找 1-2 名一线人员进行半天影子观察，但现有证据中没有完成这项研究。直到 8 月真机和线上体验，才发现集中拍照、离站前后审核、签到口径和相机拉起等真实习惯。

**根因：** AI 和内部自动化能快速填补“系统应该怎样工作”的细节，反而让团队低估了观察真实工作的重要性。

### 8.4 先设计技术状态，再寻找用户责任人

影像资格最典型：为了完整表达来源、评估、核录、整改、作废和恢复，系统增加多个状态和入口，但没有先问“谁必须据此做什么不同的动作”。

**根因：** 把数据可表达性当作业务必要性。内部规则结果被误当作用户业务状态。

### 8.5 跨模块耦合被低估

一个“照片不足不能提交”的需求会同时影响签到、检查项、工单、附件、审核、通知、档案、统计、补拍、弱网和历史兼容。早期按单页面或单接口修改，后期必须反复补齐旁路。

**根因：** 缺少业务对象生命周期图、权威字段和所有状态迁移入口清单。

### 8.6 内部验证的结论过满

7 月 30 日内部角色走查明确没有真实用户、没有 SUS、没有真机，但 8 月 3 日又记录 40 项全部通过，容易让团队误以为可用性已经收口。

**根因：** “问题台账关闭率”和“产品可用性”没有分开。自动化适合确认已知问题，不擅长发现用户心智和现场环境问题。

### 8.7 版本管理在错误阶段过度精细

标签不可变和候选保护本身正确，但在产品口径尚未稳定时连续冻结历史版本，造成重复全量测试、文档同步和证据整理。

**根因：** 把“可追溯”扩大成“每次修正都发布化”，没有区分开发验证和正式发布候选。

### 8.8 AI 协作缺少持久主线

多任务协作提高了局部处理速度，也出现口径漂移、模型不适配、补充消息导致原主线断开、代理提前扩展和同一问题被多次重新解释。

**根因：** 主任务没有始终维护唯一问题清单、当前断点、产品不变量和写入所有权；依赖聊天上下文代替仓库内持久规则。

## 9. 当前产品全景

### 9.1 已具备的能力

- Web 已覆盖运营驾驶舱、告警、工单、巡检计划、异常闭环、统一审核、站点与资产、影像与记录、数据分析、绩效和权限管理。
- 小程序已覆盖今日任务、现场巡检、站点、工单、告警、消息、计划、车辆和个人工作入口。
- 后端已形成角色与站点范围、计划执行、工单、附件、审核、通知、资源、审计和统计的主要业务基础。
- 历史发布门禁已有自动测试、构建、语法、候选校验、备份和回滚意识。

### 9.2 当前真实状态

| 方面 | 当前判断 | 证据边界 |
| --- | --- | --- |
| 产品完整度 | 功能广度高，主要业务对象已覆盖 | 不代表所有角色能稳定完成真实任务 |
| Web 管理端 | 多轮真实 UI 已修正大量布局、错误反馈和口径问题 | 当前未提交工作树未进行一次完整候选级复验 |
| 小程序现场端 | 核心路径和大量状态逻辑已有自动测试 | 真机相机、权限恢复、弱网、返场两类来源和跨页状态仍是当前关键验证面 |
| 数据与权限 | 服务端校验和回滚测试明显增强 | `backend/app.py` 体量和多业务耦合仍带来回归风险 |
| 发布状态 | 历史 r5/r6 有完整门禁记录 | 当前开发线不是已冻结候选，不能沿用历史结论直接部署 |
| 产品指标 | 已定义线上闭环率和三类角色指标 | 尚无连续 2-4 周真实基线，不能证明系统已减负或提升采用率 |

### 9.3 当前最重要的产品债

1. **现场事实仍未完全统一。** 到站、离站、返场、工单签到、检查项开放和照片权限必须在四处给出同一结论。
2. **最新小程序真实验证未完成。** 水印相册与现场相机的来源分流虽有模块测试，仍需开发者工具和真机验证。
3. **当前版本边界不清晰。** 大量未提交修改意味着历史候选、线上版本和当前开发线是三个不同对象。
4. **真实采用效果没有数据。** 北极星和角色指标仍停留在定义，没有基线、目标和月度趋势。
5. **管理端性能与信息密度仍需真实数据验证。** 地图、站点切换、筛选、长列表和弹窗在真实数据量下曾暴露卡顿和遮挡。
6. **工程结构承载过多领域。** 单体 `app.py` 使一次跨模块修改很难证明没有影响其他业务，但当前阶段也不适合无目标大重构。

## 10. 未来方向

### 阶段 0：先收敛当前候选，不扩功能

目标：形成一个可解释、可复验、可部署的唯一当前版本。

- 完成当前已授权缺陷的最小修正和只读 Review；
- 真实验证相机、水印相册、权限恢复、签到一致、返场补拍和弱网重试；
- 用同一问题清单确认七组已有反馈没有回归；
- 排除隔离数据库、测试照片、IDE 私有配置和自动化临时产物；
- 只在上述工作完成后执行一次全量门禁和冻结。

### 阶段 1：建立真实使用基线（2-4 周）

目标：回答系统是否真正减少工作，而不是继续凭感觉优化。

- 至少观察 2 名运维、1 名审核员、1 名管理员完成真实任务；
- 记录单站巡检耗时、一次提交通过率、审核耗时、失败自愈率和线上闭环率；
- 建立“系统外完成原因”分类：不会用、不愿用、系统失败、流程不适用、无网络或权限错误；
- 对线上错误、接口 P95、上传失败、弱网队列和通知失败建立可观测基线。

### 阶段 2：按任务简化，而不是按模块继续扩展

优先收敛四条主任务：

1. 今日任务 → 到站 → 检查/处置 → 证据 → 提交；
2. 异常/工单 → 接单 → 到场 → 处置 → 审核 → 关单；
3. 计划 → 资源确认 → 审批 → 执行包；
4. 管理者待办 → 查看决策信息 → 通过/退回 → 跟踪恢复。

对每条主任务删除重复入口、技术状态、无责任动作和仅为展示存在的字段。影像、设备、试剂、车辆和档案作为任务上下文或管理支撑，不再自然获得一级流程地位。

### 阶段 3：让管理端从“看系统”转向“做决策”

- 工作台默认展示需要采取行动的事项，而不是堆叠统计卡；
- 统计必须可下钻到责任人、站点和业务对象；
- “无数据、加载失败、真实为 0、没有权限”必须是不同结论；
- 当前有效视图与历史审计视图分开，默认不混排；
- 报表直接复用页面权威口径，不独立计算一套指标。

### 阶段 4：有证据后再投资智能化和架构升级

只有出现以下证据时，才进入相应投资：

| 方向 | 进入条件 |
| --- | --- |
| AI 图片预筛 | 有足够标注样本，漏审率和误报率可量化，且责任制度允许辅助判断 |
| 路线优化 | 真实路线折返造成显著时间或里程损失，现有简单建议不足 |
| 数据库与服务拆分 | SQLite 并发、单体部署或 `app.py` 耦合已形成可测量性能或交付瓶颈 |
| 完整离线闭环 | 真实站点弱网导致核心任务失败达到明确频率，轻量重试不足 |
| 新模块 | 有独立用户、独立责任、独立动作和独立业务结果，且不能自然嵌入现有主任务 |

### 明确不做

- 不为“看起来专业”增加用户必须理解的技术状态；
- 不为每个数据表增加独立页面；
- 不在没有基线时承诺 AI、预测或最优调度价值；
- 不用人工核录替系统补造可信事实；
- 不把所有临时工作强塞进巡检计划；
- 不在开发口径仍变化时反复创建候选和执行全量冻结。

## 11. 适合本项目的产品经理工作模式

### 11.1 八步决策法

每个产品问题按固定顺序处理：

1. **用户**：谁在什么场景受阻；
2. **损失**：多花时间、无法完成、数据错误、责任不清还是安全风险；
3. **事实**：UI、接口、数据库、日志和用户行为分别证明什么；
4. **问题**：穿透用户给出的解决方案，定义真正需要改变的结果；
5. **责任**：应该由系统、运维、审核员还是管理员承担判断和动作；
6. **最短闭环**：用最少新概念让用户完成任务并能从失败恢复；
7. **边界**：权限、弱网、重复、并发、跨日、旧数据、旧客户端和异常回滚；
8. **证据**：什么自动测试、真实 UI、真机和业务数据才足以宣称完成。

### 11.2 六道产品门

| 门 | 必须回答的问题 | 不满足时的动作 |
| --- | --- | --- |
| 机会门 | 问题频率、影响角色和当前替代方式是什么 | 不进入设计 |
| 方案门 | 是否有更短路径；是否新增了用户学习成本 | 继续做减法 |
| 开发门 | 业务对象、责任、状态、时间、权限和失败恢复是否清楚 | 不交开发 |
| Review 门 | 是否破坏现有功能；边界、错误、类型、安全和测试是否完整 | 退回最小修正 |
| 验收门 | 真实角色能否独立完成；失败能否恢复；跨端事实是否一致 | 不宣称修复 |
| 发布门 | 唯一候选、备份、迁移、回滚、监控和真实 UI 是否齐全 | 不冻结或部署 |

### 11.3 AI 时代产品经理必须额外具备的能力

1. **问题抽象能力**：不把用户的按钮、字段或页面建议直接当需求。
2. **约束表达能力**：把业务不变量、禁止事项、文件边界和验收条件写成代理无法误解的任务契约。
3. **全局状态管理能力**：维护唯一问题清单、当前断点、写入所有者和待决问题，不依赖聊天记忆。
4. **证据分级能力**：区分代码存在、单测通过、API 通过、模拟器通过、真实 UI 通过和业务效果改善。
5. **复杂度预算能力**：每增加一个状态、入口、字段或例外处理，都要证明其用户价值大于学习和维护成本。
6. **安全自治能力**：在用户不能实时监督时，仍遵守授权范围，不擅自修改、部署、造数据或扩大问题。
7. **停止能力**：遇到产品决策、工具阻断或重复失败时及时暂停并请求确认，而不是用更多操作掩盖不确定性。

## 12. 对当前产品经理能力的诚实评价

### 已经得到本项目证据支持的能力

- 能从真实反馈中区分现象、问题和方案；
- 能识别技术状态机对用户造成的认知负担并推动简化；
- 能从权限、事务、幂等、错误恢复和真实 UI 角度做跨模块 Review；
- 能在后期复杂工作树中保护既有改动、控制范围并要求证据；
- 能反思版本仪式和多任务协作的额外成本；
- 能把临时教训转为仓库内长期规则候选。

### 尚未得到充分验证的能力

- 从零完成市场、组织目标、商业约束和竞品研究；
- 在编码前组织真实用户研究并据此裁剪第一版范围；
- 用连续业务指标证明产品带来效率和采用率提升；
- 进行跨季度路线图、预算和人力取舍；
- 推动培训、迁移、运营和组织变更，使系统成为默认工作方式；
- 在多次发布周期中证明长期产品节奏和架构治理有效。

因此，当前更准确的定位是：**已经在复杂项目后期形成较强的诊断、纠偏、审查和收敛能力，但尚不能仅凭本项目证明具备从 0 到 1、商业化和长期增长阶段的完整产品经理能力。**

## 13. 应沉淀到长期协作规则的内容

以下规则适合进入仓库长期规范，但应由用户确认后单独修改 `AGENTS.md`：

1. 产品主任务负责问题定义、口径、范围、工作清单和最终验收，不直接写业务代码；开发经理是业务代码唯一写入者。
2. 仓库维护独立的 `PRODUCT_WORK_LEDGER.md`，记录当前问题、状态、负责人、断点、证据和待决事项；当前状态不得写入长期规则。
3. 每项开发任务必须包含用户、场景、损失、目标结果、允许范围、禁止事项、业务不变量和验收证据。
4. 用户在执行中补充事实时，只更新相关事项的约束和验收条件；除非用户明确暂停，否则主线自动恢复到原断点。
5. 内部规则默认隐藏，只有影响用户动作时才转换为业务化提示；新增业务状态必须有独立责任人和独立动作。
6. 自动化、模拟器和 API 证据不能替代当前版本的真实 UI 或真机证据。
7. 开发中只跑定向测试，模块收口跑相关回归，唯一发布候选才跑一次全量门禁。
8. 产品口径未稳定时不创建候选标签；退回候选只保留历史，不移动、不复用。

当前开发线的 `AGENTS.md` 已覆盖其中多数原则，但仍有两项治理缺口：

- “简单或强耦合修改由主任务完成”与“产品经理不写业务代码”的最新职责约定冲突；
- 尚无持续维护的产品工作台账，主线仍容易依赖聊天上下文。

这两项应在用户确认后作为独立治理任务处理，不能混入当前业务修复。

## 14. 下一次复盘如何证明项目真的进步

下一次复盘不再以“完成了多少功能、修了多少问题、通过多少测试”为主，而应至少回答：

- 关键运维动作线上闭环率是多少，为什么还有动作在线下；
- 单站巡检耗时和一次提交通过率相比基线是否改善；
- 审核员单项耗时、待审 P90 和真实漏审率是否同时改善；
- 操作失败后用户自主恢复的比例是多少；
- Web 和小程序各有多少真实用户稳定使用；
- 生产 P95、5xx、上传失败、弱网同步和通知失败趋势如何；
- 过去一个月新增了多少用户可见状态和入口，又删除了多少无效复杂度；
- 有多少问题在真实使用前被发现，而不是上线后由用户发现。

当这些问题能用连续数据回答时，项目才从“功能丰富、持续修正”进入“产品有效、可持续优化”的阶段。

# 水质运维领域自治协作入口

> 状态：`ACTIVE_DOMAIN_OWNERSHIP_MODEL`
> 基线：任务开始时的远程 `origin/main`，实际起点写入分支和 PR
> 性质：开发协作基线，不是发布候选，不授权部署或生产操作

## 1. 从这里开始

每位负责人只需依次完成：

1. 阅读本文件和自己的 `A_CURRENT.md`、`B_CURRENT.md`、`C_CURRENT.md` 或 `MAIN_CURRENT.md`。
2. `git fetch origin`，记录 `git rev-parse origin/main`，从该提交创建任务分支。
3. 先确认问题、完成标准、上下游和写入范围，再开始修改。
4. 在一个 PR 内完成产品判断、实现、测试、返修和回传；按仓库 PR 模板填写，返修不新建 PR。

详细业务硬约束见 `../DEVELOPMENT_STANDARDS.md`。设计任务按需读取 `README-design.md`。旧日期交接只用于争议追溯，不是当前执行合同。

## 2. 领域责任

| 单元 | 主责领域 | 对结果负责的完整范围 |
|---|---|---|
| A | 站点与监测数据 | 站点档案、身份/MN、数据接收解析、匹配、有效观测、趋势、地图及双端监测体验 |
| B | 巡检与现场执行 | 计划、检查项、到站、影像证据、提交、审核、整改和执行档案 |
| C | 异常与运维资源 | 告警、工单、车辆、设备、物资、备件、试剂和资源占用 |
| 主线 | 平台与集成 | 人员权限、审批、消息、首页/我的、公共交互、审计、跨域治理、版本和发布交接 |
| 本地设计支持 | 横向设计系统 | 由主线安排静态设计和实际渲染复核，不是远程协作者，不独立集成代码 |

领域负责人不是单一页面开发者，而是本领域的产品、全栈开发、测试和维护负责人。需要主动理解用户、维护问题池、提出下一事项，并对 Web、小程序、后端、数据和测试的完整结果负责。

## 3. 决策权限

领域负责人可独立决定并实施：

- 已确认业务规则下的缺陷修复和体验改进。
- 本领域内部的非破坏性接口扩展、展示映射和局部重构。
- 测试补充、错误可见性、重试和兼容性修正。
- 从本人工作台 `READY` 候选中启动下一项低风险工作。

下列事项必须先经主线产品裁决：

- 新增或删除业务流程、页面主入口、状态、角色能力或审核环节。
- 修改公共接口、公共数据模型、全局导航、权限边界或审计规则。
- 物理删除、不可逆迁移、生产操作、候选冻结和部署。
- 两个领域对业务归属、接口语义或优先级无法达成一致。

用户当次明确要求始终优先。

## 4. 一个变更，一个结果负责人

领域归属不是文件围墙。每项变更只指定一名结果负责人，按最终业务结果归属确定，而不是按修改文件数量确定。

### 领域内变更

负责人独立完成问题分析、全栈实现、定向测试和 PR，不等待主线逐步派单。

### 跨域但可按契约分离

1. 结果负责人先写清用户结果、接口输入输出、权限、状态、错误和兼容要求。
2. 受影响领域负责人先 Review 契约，再各自并行实现；消费者可先用 Mock 或固定样例开发。
3. 结果负责人负责最终接线和端到端验证，不通过用户传话。

### 强重叠或同文件修改

主线指定一名临时变更负责人并记录允许文件；其他负责人停止重叠写入，只做契约和代码 Review。任务结束后，长期责任自动回归原领域。

任何时候同一文件只能有一个活动写入者。发现重叠时先协调写入权，不允许用后合并解决并发覆盖。

## 5. 跨域契约最小格式

跨域开发前，在结果负责人的 `CURRENT` 或 PR 描述中写清：

- 业务结果和结果负责人。
- 提供方、消费方及受影响领域。
- 请求、响应、状态、权限、错误和幂等规则。
- 向后兼容方式及 Mock/样例。
- 文件临时写入权、合并顺序和端到端验收人。

契约未确认前可以只读调查，不得分别猜测字段并开始两套实现。

## 6. 自主工作循环

每位负责人持续执行同一循环：

1. 从真实反馈、代码、数据和现有流程中发现问题。
2. 区分现象、问题和方案，说明用户、场景、损失和完成标准。
3. 核对上下游、权限、状态、数据和直接相邻回归。
4. 判断是领域内、契约分离还是强重叠变更。
5. 更新本人 `CURRENT` 的当前事项和写入边界，在分支完成实现。
6. 自检、运行风险相称的测试并创建 PR。
7. 处理原 PR 内返修；合并后清理已闭环内容并选择下一个 `READY` 候选。

负责人不得把“等待下一条指令”作为常态。没有活动事项时，应从本领域提出三个候选并给出优先级依据。

## 7. Review 与合并

- 作者先完成产品自检、代码自检和范围内测试。
- 受影响领域负责人只审其契约、数据和业务风险，不接管结果责任。
- 主线 Review 公共能力、跨域一致性、高风险操作及前两轮领域接管成果；普通领域内改动逐步转为抽查。
- `代码 Review PASS`、`设计静态 Review PASS`、`真实 UI PASS`、`已合并` 和 `已部署` 必须分别记录。
- PR 合并前只需在必要时同步一次最新 `main`；不要在每条 Review 意见后反复拉取。
- 合入 `main` 不代表发布。冻结和部署仍由独立发布流程执行。

## 8. 设计协作

有明显信息架构或交互变化时：

1. 领域负责人提交产品骨架和不可变业务边界。
2. 主线安排本地设计师完成静态方案，静态 Review 后把可执行设计基线纳入仓库。
3. 结果负责人按设计基线接线业务；设计师停止重叠写入。
4. 可运行后由设计师复核实际渲染，独立真实 UI 验收再判断行为结果。

纯接口、数据、权限或无视觉变化的修复不强制经过设计师。

## 9. `CURRENT` 工作台规则

四份 `CURRENT` 同时承担领域章程和当前断点，不是过程日志。负责人负责维护本人文件，固定保留：

- 领域目标与核心链路。
- 代码、接口、数据和测试地图。
- 不可变规则及上下游。
- 当前事项、当前写入权和停点。
- `READY` 下一候选及真实阻断。

完成后删除旧返修步骤和重复证据，只保留仍影响执行的结论。不得按日期无限追加章节，也不得新建平行台账。

## 10. 当前切换期

- 当前 A/B/C PR 按各自工作台原范围完成，作为首轮训练，不推倒重来。
- 首轮合并后，每位负责人完成一次领域接管：跑通核心链路、核对代码地图、提出三个有依据的候选事项。
- A 是当前站点 Tab 的结果负责人；C 提供试剂契约并与 A 直接对齐；主线只处理现有本地设计资产和最终冲突治理。
- B 完成当前 Web 收口后，回归巡检与现场领域并完成领域接管。
- 真实 UI、冻结和部署不因协作模式切换而自动通过。

## 11. 即时协作消息

群聊用于告知“下一步轮到谁”，不代替 PR、交接、测试证据或发布授权。只在需要他人行动时发送；普通提交和同一人的连续工作不逐条广播。发起人直接 @ 下一行动人，接收者回复“已接手，下一步是……”或“暂不能接手，原因是……”。未获确认时，可继续不重叠工作，但不得把依赖项视为完成。群聊对独立 AI 任务不一定可见，任务操作者须把关键消息转给相应任务；持久结论仍落在 PR 或当前交接。

```text
【类型｜模块｜当前状态】@下一行动人
已完成/发现：一句话事实或结果。
请你做：一个明确动作；需拍板时给选项和推荐意见。
依据：PR、交接或验收证据链接；没有则写“待补”。
时点/阻断：是否挡住后续；仅有真实期限时写时间。
```

类型使用 `协作请求`、`接棒`、`待Review`、`返修意见`、`返修回传`、`待拍板`、`发布申请`、`发布回传`、`阻断`。跨域问题由结果负责人直接联系提供方并负责最终接线；主线只接收需产品裁决、跨域冲突、高风险 Review 和集成的请求。`发布申请` 只是请求，用户明确批准且冻结交接有效后才由独立发布任务执行。不得在群内发送凭据或私有配置。

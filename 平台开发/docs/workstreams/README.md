# 水质运维领域自治协作入口

> 状态：`ACTIVE_DOMAIN_OWNERSHIP_MODEL`
> 基线：任务开始时的远程 `origin/integration`，实际起点写入分支和 PR
> 性质：开发协作基线，不是发布候选，不授权部署或生产操作

## 1. 从这里开始

每位负责人依次完成：

1. 阅读本文件和自己的 `A_CURRENT.md`、`B_CURRENT.md`、`C_CURRENT.md` 或 `MAIN_CURRENT.md`，只用于理解稳定领域地图和候选问题，不把它们当作当前执行指令。
2. 多人共同完成一个结果时，先阅读 `BATCH_RESULT_OWNER_COLLABORATION_EXPERIENCE_20260928.md`，按批次结果负责人模式组织，不把每个子 PR 分别交主产品 Review。
3. 等待产品主线依据唯一产品台账指定开发树内的一份自包含交接；未取得该交接时只能调查、提出候选和做只读 Review，不得据 `CURRENT`、PR 或群消息直接开始写入。
4. 收到交接后核对目标、唯一写入者、允许/禁止文件、输入契约、验收、测试和停点，再从最新 `origin/integration` 或交接指定的 `batch/*` 创建任务分支。
5. 单人批次在一个 PR 内完成实现、测试、返修和回传；多人批次的子 PR 先进入结果负责人的 `batch/*`，最终只提交一个完整候选到 `integration`。PR 只摘要交接和证据，不能替代执行合同。

详细业务硬约束见 `../DEVELOPMENT_STANDARDS.md`。设计任务按需读取 `README-design.md`。旧日期交接只用于争议追溯，不是当前执行合同。

## 2. 领域责任

| 单元 | 主责领域 | 对结果负责的完整范围 |
|---|---|---|
| A | 站点与监测数据 | 站点档案、身份/MN、数据接收解析、匹配、有效观测、趋势、地图及双端监测体验 |
| B | 巡检与现场执行 | 计划、检查项、到站、影像证据、提交、审核、整改和执行档案 |
| C | 异常与运维资源 | 告警、工单、车辆、设备、物资、备件、试剂和资源占用 |
| 主线 | 平台与集成 | 人员权限、审批、消息、首页/我的、公共交互、审计、跨域治理、集成验收、版本和发布交接 |
| 各领域设计师 Agent | 本领域专业设计 | 由 A、B、C 和主线分别建立并管理，遵循同一设计规范与设计系统，对本领域静态设计和设计 Review 负责 |

领域负责人不是单一页面开发者，需要主动理解用户、维护问题池、提出下一事项，并对本领域最终结果负责；业务代码仍由当前交接授权的开发经理作为唯一写入者完成。

### 设计与开发边界

“全栈负责”是对业务链路、接口、权限、前后端接线和测试负责，不代表开发者自行决定视觉方案。

- 新布局、信息层级、卡片结构、筛选层级或图标体系必须先标记 `DESIGN_REQUIRED`。结果负责人可在自己的领域建立专业设计师 Agent，按统一设计规范和现有设计系统形成静态方案；设计师只有在用户明确授权的限定 UI 文件内才可直接写代码。
- 已有设计下的接口接线、权限、状态、错误和数据映射由当前交接授权的开发经理实现；任何时候同一批次、同一文件只有一个业务代码写入者。
- 首页、我的、全局 TabBar、公共页头、设计令牌和共享组件归主线领域。其他负责人如确需修改，先由主线在自包含交接中明确跨域影响和临时写入权。
- 设计师 Agent 完成静态方案或限定 UI 实现后停止重叠写入，再由开发经理接线和集成；代码 Review、设计静态 Review 和真实 UI 必须分别表述。

## 3. 共享集成与生产分支

- `main` 是唯一生产事实分支，只指向已经实际部署且生产后验通过的提交。A/B/C 不直接向 `main` 提交协作 PR。
- `integration` 是唯一共享合并、跨域联调和真实 UI 验收分支。领域 PR 默认以它为目标；合入 `integration` 不等于已冻结、可发布或已经上线。
- 单人批次的 `collab/*` 从最新 `origin/integration` 创建。多人批次由结果负责人从最新 `origin/integration` 创建 `batch/*`，子任务分支和子 PR 先进入该批次分支；最终仅由 `batch/*` 向 `integration` 提交完整候选。
- 批次外的跨域依赖只有进入 `integration` 后，其他领域才能作为共享基线消费；同一批次内按冻结契约和结果负责人安排的顺序接线。
- `integration` 验收通过后从不可变提交形成发布候选；独立发布任务部署并完成生产后验后，`main` 才快进到该已部署提交。
- 紧急修复从 `main` 建 `hotfix/*`，验证和上线后更新 `main`，并立即同步回 `integration`。

## 4. 决策权限

领域负责人可独立调查、判断并提出：

- 已确认业务规则下的缺陷修复和体验改进。
- 本领域内部的非破坏性接口扩展、展示映射和局部重构。
- 测试补充、错误可见性、重试和兼容性修正。
- 从本人候选池中推荐下一项低风险工作及优先级；正式写入仍须由产品台账指定自包含交接和唯一写入者。

下列事项必须先经主线产品裁决：

- 新增或删除业务流程、页面主入口、状态、角色能力或审核环节。
- 修改公共接口、公共数据模型、全局导航、权限边界或审计规则。
- 物理删除、不可逆迁移、生产操作、候选冻结和部署。
- 两个领域对业务归属、接口语义或优先级无法达成一致。

用户当次明确要求始终优先。

## 5. 一个变更，一个结果负责人

领域归属不是文件围墙。每项变更只指定一名结果负责人，按最终业务结果归属确定，而不是按修改文件数量确定。

### 领域内变更

负责人独立完成问题分析、全栈实现、定向测试和 PR，不等待主线逐步派单。

### 跨域但可按契约分离

1. 结果负责人先写清用户结果、接口输入输出、权限、状态、错误和兼容要求。
2. 受影响领域对契约提供确认或异议，不建立独立产品 Review 门禁；消费者可先用 Mock 或固定样例开发。
3. 子 PR 进入结果负责人的批次分支，结果负责人负责最终接线、冲突处理和端到端验证，不通过用户传话，也不把半成品分别交主产品 Review。

### 强重叠或同文件修改

主线指定一名临时变更负责人并记录允许文件；其他负责人停止重叠写入，只做契约和代码 Review。任务结束后，长期责任自动回归原领域。

任何时候同一文件只能有一个活动写入者。发现重叠时先协调写入权，不允许用后合并解决并发覆盖。

## 6. 跨域契约最小格式

跨域开发前，由产品主线在开发树自包含交接中写清；PR 只摘要并链接该交接：

- 业务结果和结果负责人。
- 提供方、消费方及受影响领域。
- 请求、响应、状态、权限、错误和幂等规则。
- 向后兼容方式及 Mock/样例。
- 文件临时写入权、合并顺序和端到端验收人。

契约未确认前可以只读调查，不得分别猜测字段并开始两套实现。

## 7. 自主工作循环

每位负责人持续执行同一循环：

1. 从真实反馈、代码、数据和现有流程中发现问题。
2. 区分现象、问题和方案，说明用户、场景、损失和完成标准。
3. 核对上下游、权限、状态、数据和直接相邻回归。
4. 判断是领域内、契约分离还是强重叠变更。
5. 把候选和依据提交主线；主线在唯一产品台账中确定下一动作并指定开发树自包含交接。
6. 当前唯一写入者按交接在分支实现、自检、运行风险相称的测试并创建 PR。
7. 处理原 PR 内返修；合并后更新稳定领域地图并提出下一候选。

负责人不得把“等待下一条指令”作为常态。没有活动事项时，应从本领域提出三个候选并给出优先级依据；主动发现不等于自行取得代码写入权。

## 8. Review 与合并

- 作者自检、范围内测试、契约确认和结果负责人汇总都是交付准备，不分别建立正式 Review 停点。
- 多人批次由结果负责人先接入全部子项、解决冲突并形成一个完整候选；主线不逐个审批简单子 PR。
- 默认只保留两道最终质量关口：主产品对完整候选做一次代码、产品与上下游 Review；合入 `integration` 后由独立任务做一次真实 UI 验收。
- 高风险事项通过定向测试、事务、预览、备份和回滚证据加强；只有产品规则变化、跨域冲突或不可逆动作才提前升级，不机械增加人员 Review。
- `代码 Review PASS`、`设计静态 Review PASS`、`真实 UI PASS`、`已合并` 和 `已部署` 必须分别记录。
- 真实 UI 返修只复验失败项及直接相邻区域；没有范围变化时不重启整批 Review。PR 合并前只需在必要时同步一次最新 `integration`，不要在每条意见后反复拉取。
- 合入 `integration` 只代表进入共享联调与验收，不代表冻结、发布或已上线。

## 9. 设计协作

有明显信息架构或交互变化时：

1. 领域负责人提交产品骨架和不可变业务边界，并在本领域建立专业设计师 Agent。
2. 本领域设计师 Agent 按统一设计规范和现有设计系统完成静态方案；静态 Review 后把可执行设计基线纳入同一领域分支或交接。
3. 产品主线形成自包含开发交接，由当前开发经理作为唯一业务代码写入者按设计基线接线；设计师 Agent 停止重叠写入。
4. 可运行后由本领域设计师 Agent 复核实际渲染，独立真实 UI 验收再判断行为结果；跨域冲突和公共组件变更再交主线裁决。

纯接口、数据、权限或无视觉变化的修复不强制经过设计师。

## 10. `CURRENT` 工作台规则

四份 `CURRENT` 只承担稳定领域章程、代码地图和候选问题池，不是产品断点、执行交接或写入授权。唯一产品断点始终是产品树 `PRODUCT_WORK_LEDGER.md`，开发只执行该台账指定的开发树自包含交接。`CURRENT` 固定保留：

- 领域目标与核心链路。
- 代码、接口、数据和测试地图。
- 不可变规则及上下游。
- 候选事项、依据、依赖及真实阻断。

完成后删除旧返修步骤、临时写入说明和重复证据，只保留仍影响领域判断的结论。不得按日期无限追加章节，也不得用 `CURRENT` 建立平行台账。

## 11. 当前切换期

- 当前 A/B/C PR 按各自工作台原范围完成，作为首轮训练，不推倒重来。
- 首轮合并后，每位负责人完成一次领域接管：跑通核心链路、核对代码地图、提出三个有依据的候选事项。
- A 是当前站点 Tab 的结果负责人；C 提供试剂契约并与 A 直接对齐；A 自行调度本领域设计师 Agent，主线只处理公共能力和最终冲突治理。
- B 完成当前 Web 收口后，回归巡检与现场领域并完成领域接管。
- 真实 UI、冻结和部署不因协作模式切换而自动通过。

## 12. 即时协作消息

群聊用于告知“下一步轮到谁”，不代替 PR、交接、测试证据或发布授权。只在需要他人行动时发送；普通提交和同一人的连续工作不逐条广播。发起人直接 @ 下一行动人，接收者回复“已接手，下一步是……”或“暂不能接手，原因是……”。未获确认时，可继续不重叠工作，但不得把依赖项视为完成。群聊对独立 AI 任务不一定可见，任务操作者须把关键消息转给相应任务；持久结论仍落在 PR 或当前交接。

```text
【类型｜模块｜当前状态】@下一行动人
已完成/发现：一句话事实或结果。
请你做：一个明确动作；需拍板时给选项和推荐意见。
依据：PR、交接或验收证据链接；没有则写“待补”。
时点/阻断：是否挡住后续；仅有真实期限时写时间。
```

类型使用 `协作请求`、`接棒`、`待Review`、`返修意见`、`返修回传`、`待拍板`、`发布申请`、`发布回传`、`阻断`。跨域问题由结果负责人直接联系提供方并负责最终接线；主线只接收需产品裁决、跨域冲突、高风险 Review 和集成的请求。`发布申请` 只是请求，用户明确批准且冻结交接有效后才由独立发布任务执行。不得在群内发送凭据或私有配置。

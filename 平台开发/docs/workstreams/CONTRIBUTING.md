# 设计贡献指南

> 想给设计系统加东西？按这个流程来。
> 设计系统是公共资产，不是谁想加就加，加了就要维护。

---

## 什么时候需要贡献到设计系统？

### ✅ 应该加的
- 一个组件在 3 个以上不同页面复用
- 一个 Token 在多个地方用到，且语义明确
- 一个交互模式反复出现，可以抽象成标准模式
- 修复设计系统本身的 Bug（Token 错误、组件规格不准确）

### ❌ 不应该加的
- 只在一个页面用的特殊样式 → 写在页面级 WXSS 里
- 一次性的业务展示 → 用现有组件组合
- 只是个人偏好的样式调整 → 按设计系统来，不改
- "以后可能会用到"的组件 → 等真用到了再加

## 新增 Token 流程

### 第一步：确认真的需要
- [ ] 现有的语义 Token 里没有能用的？
- [ ] 不是只在一个页面用一次？
- [ ] 语义明确，不会跟现有 Token 混淆？

如果有任何一个答不上来，先使用最接近的既有语义 Token 或在 PR 中提出待确认项；不要用页面级自定义颜色临时绕过规则。

### 第二步：按层级加

Token 三层结构，从下往上加：

```
1. Palette（原始色板）：先加色值
   --palette-xxx-500: #xxxxxx;

2. Semantic（语义层）：映射到语义
   --color-xxx: var(--palette-xxx-500);

3. Component（组件层）：组件专用（可选）
   --button-xxx-bg: var(--color-xxx);
```

**不是每加一个颜色就要加一个色板层级。**
如果新 Token 只是现有颜色的另一种语义用法，直接映射就行。

### 第三步：同步更新
设计资产已纳入当前任务范围且修改 `colors_and_type.css` 之后：
1. 使用设计系统转换脚本重新生成 `css.json`；脚本未纳入当前分支时，标记缺口并停止，不手工伪造生成物
2. 更新小程序 `app.wxss` 中的桥接变量
3. 在 PR 说明里列出新增了哪些 Token、用在什么地方

## 新增组件流程

### 第一步：提案（Proposal）
在团队里提出来，说明：
- 组件叫什么名字
- 解决什么问题
- 哪些页面会用到（至少 3 个场景）
- 现有组件为什么满足不了

团队确认值得做，再进入下一步。别自己闷头写了一个，最后大家都不用。

### 第二步：定义规格
写组件的 JSON 规格文件（`components/{slug}.json`），包含：
- 名称、分类、优先级
- 变体（variants）：有几种样式
- 状态（states）：默认/hover/active/disabled/loading 等
- 使用场景（whenToUse）
- 不使用场景（whenNotToUse）
- 规格尺寸（sizes）：高度、圆角、间距、字号
- Token 依赖：用到了哪些设计 Token

### 第三步：做预览页
写组件的 HTML 预览页（`preview/component-{slug}.html`），
展示所有变体和状态，让人一眼看懂长什么样。

### 第四步：更新索引
在 `components/index.json` 里加上新组件，
在仓库 `README-design.md` 的组件清单里补上；源设计资产纳入提交时同步更新其 README。

### 第五步：Review
至少一个人 Review 通过，关注点：
- 命名是否清晰、有没有歧义
- 规格是否完整、有没有遗漏状态
- 有没有跟现有组件功能重叠
- Token 使用是否规范

## 修改现有组件的流程

### 小改（Bug 修复、参数补充）
直接改，PR 说明清楚改了什么、为什么改。

### 大改（变体新增、尺寸调整、视觉风格变化）
- 先确认影响范围：哪些页面用了这个组件？
- 改完之后，所有用到的页面都要回归检查
- 在 PR 里列出受影响的页面列表

## 新增图标

### 图标规范
- 线性风格，24×24 画布，2px 线宽，圆角端点
- 使用 `currentColor` 填充，不写死颜色
- 命名：`kebab-case`，如 `water-drop.svg`、`calendar-check.svg`

### 什么时候加
- 图标在多个页面复用
- 现有图标库里没有语义接近的

### 怎么加
1. SVG 文件放到 `icons/` 目录
2. 在仓库 `README-design.md` 图标分类里加上；源设计资产纳入提交时同步更新其 README
3. 在 `preview/icons.html` 里加上预览

## 文档贡献

发现文档写错了、写漏了、看不懂，可以在任务分支修改：
- 错别字、格式问题 → 随当前 PR 一并 Review
- 内容补充、结构调整 → PR + Review
- 规则变更（改铁律、加新规范）→ 团队讨论后再改

文档也是代码的一部分，不要让错误的文档留在那里。

## 版本号规则

设计系统版本号：`主版本.次版本.修订版本`

| 版本 | 说明 | 例子 |
|------|------|------|
| 修订版本（patch） | Bug 修复、文档补充、小调整 | 1.2.0 → 1.2.1 |
| 次版本（minor） | 新增组件、新增 Token、新增文档 | 1.2.0 → 1.3.0 |
| 主版本（major） | 大规模重构、风格改版、不兼容变更 | 1.2.0 → 2.0.0 |

设计规范形成新版本时，更新 `README-design.md` 中的版本历史。

## 设计债务（Design Debt）

有些时候为了赶工期，会先写硬编码、先不抽组件。
这很正常，但要记下来，不能让债务越积越多。

### 怎么记
在代码里用 `TODO(design):` 注释标记：
```css
/* TODO(design): 这个颜色应该加到设计系统里，等 v1.4 统一处理 */
background: #FF6B81;
```

然后在团队的任务看板里建一条对应的 Tech Debt 任务。

### 什么时候还
- 每个迭代由产品根据优先级安排适量设计债务，不预设固定比例
- 做大版本重构时，顺便清理一波
- 新功能开发时，如果改到了有 TODO 的地方，顺手还了

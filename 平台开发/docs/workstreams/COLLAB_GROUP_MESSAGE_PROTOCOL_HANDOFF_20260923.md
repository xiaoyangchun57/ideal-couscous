# A/B/C 协作群消息规范交接

> 状态：协作规则已形成，待 A/B/C 接收并启用。适用于三位远程领域负责人和产品主线，不改变各 PR 的范围、写入权、Review 结论或发布状态。

## 目标与责任

解决“PR 已更新但下一人不知道该行动、产品不知道何时拍板”的通知缺口。每项变更仍由原结果负责人负责到底；跨域提供方直接与结果负责人对接，产品主线不替他们传技术消息。主线维护共享规则，A/B/C 不各自修改共享 `AGENTS.md` 或 `workstreams/README.md` 形成冲突。

## 启用动作

1. 用户把本文件的仓库路径发给 A/B/C，并建立或沿用包含用户、A、B、C 的协作群；选定群聊工具即可，不要求额外看板或机器人。
2. A/B/C 各自在自己的任务中把本文件作为长期协作约束，回复一次“已接收”；以后按下述格式主动发可行动消息。若独立 AI 任务不能访问群聊，其操作者负责把相关群消息转给任务，不得假定 AI 已读。
3. 主线也按同一格式发送 Review、返修和需拍板消息，并对被 @ 的请求明确回复“已接手/暂不能接手”。开发树共享 `AGENTS.md` 和 `workstreams/README.md` 记录同一规则；产品树本地 `AGENTS.md` 已同步。

## 唯一消息格式

只在行动人变化或需要对方行动时发；普通提交、个人进度和同一人连续返修不逐条广播。

```text
【类型｜模块｜当前状态】@下一行动人
已完成/发现：一句话事实或结果。
请你做：一个明确动作；需拍板时给选项和推荐意见。
依据：PR、交接或验收证据链接；没有则写“待补”。
时点/阻断：是否挡住后续；仅有真实期限时写时间。
```

类型限 `协作请求`、`接棒`、`待Review`、`返修意见`、`返修回传`、`待拍板`、`发布申请`、`发布回传`、`阻断`。接收者在同一讨论串或群内回复“已接手，下一步是……”或“暂不能接手，原因是……”。发出不等于已交接；等待确认期间可继续非重叠工作，不得把依赖项当作完成。PR/交接是正式执行依据和结论，群消息只负责触达；不得在群内发凭据或私有配置。

## 三类常用示例

```text
【协作请求｜站点试剂｜待接口核对】@C
已完成：A 已在原 PR 接入删除接口。
请你做：核对与后端权限、错误码及幂等语义，回复可接线或差异。
依据：A、C 的原 PR 链接。
阻断：只挡试剂联调，其他站点工作可继续。

【返修回传｜巡检计划｜待复审】@主线
已完成：修正上一轮第 2 项并补直接 API 定向测试。
请你做：复审该项并给明确结论。
依据：原 PR 链接及测试结果；真实 UI NOT RUN。
阻断：复审前不宣称验收通过。

【发布申请｜冻结候选｜待用户授权】@用户 @发布负责人
已完成：候选标签与冻结交接已准备，验收结论见交接。
请你做：用户决定是否批准；明确授权后由独立发布任务执行。
依据：冻结交接链接和不可变标签。
阻断：没有授权不打包、不部署。
```

## 验收与停点

- A/B/C 各确认收到并能发出一条指向真实下一行动人的消息；主线对其中一条需要自己行动的消息作接收确认。该确认只验协作链路，不等于业务 PR Review 或真实 UI PASS。
- 不要求为消息单独开 PR、增加工作台日志、频繁同步 `main`；接收确认不是发布授权或代码验收，发布须用户明确批准。既有 PR 按原边界继续。
- 本文件不授权其他代码提交、合并、冻结或部署；避免 A/B/C 各改一版共享规则。当前协作规则的提交和推送由用户另行明确授权，不表示业务 PR 可合并。

回传只需每人一句：`已接收；当前下一行动人是 X；等待/不等待其确认；对应 PR 为 Y`。如有冲突，指出哪条现有执行边界与本规范不兼容，由主线一次裁决。

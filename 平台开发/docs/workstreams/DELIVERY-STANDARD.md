# 设计交付标准

> 一个功能做完了，交付什么、怎么交、交之前查什么，全在这里。
> 各执行单元分别交付，但格式统一，别人接手就能看懂。

设计静态交付与开发接线交付是两个停点，不能互相冒充完成。设计师只需提交本轮允许的设计稿、UI 文件和状态说明；开发接线完成后，才要求可运行代码、接口映射和自动测试。

---

## 1. 交付物清单

每个功能页面/模块按当前所处停点提交适用内容；不适用项标记 `N/A`，未验证项标记 `NOT RUN`，不得假报完成。

### 1.0 设计静态交付
- [ ] 页面层级、关键组件和允许修改的 UI 文件已明确
- [ ] 加载、空态、错误、禁用、提交中、失败保留、成功和长内容等适用状态已覆盖
- [ ] 与当前业务字段、权限和状态的对应关系已说明，但未擅自改业务契约
- [ ] 已写清开发接线边界及静态 Review 停点

### 1.1 开发接线代码
- [ ] 页面 WXML + WXSS + JS + JSON 完整可用
- [ ] WXSS 中无硬编码色值（grep 验证）
- [ ] 所有交互状态都实现了（默认/填写中/提交中/成功/失败）
- [ ] 空状态、加载态、错误态都有处理

### 1.2 状态枚举表
- [ ] 列出所有状态值 → 显示文案 → 语义色 → 对应操作
- [ ] 状态命名遵循 `DEV-HANDOFF.md` 的标准映射
- [ ] 新增了自定义状态？必须在 PR 说明里标注并申请 Review

### 1.3 字段映射表
- [ ] 接口字段 → 页面展示位置的对应关系
- [ ] 表单字段：类型、必填、校验规则、错误文案
- [ ] 列表字段：每个位置对应哪个字段

### 1.4 交互流程说明
- [ ] 按钮点击 → 调什么接口 → 成功做什么 → 失败做什么
- [ ] Sheet / 弹窗的打开关闭逻辑
- [ ] 页面间跳转关系（从哪来、到哪去、返回刷新不刷新）

### 1.5 边界情况说明
- [ ] 无数据时展示什么
- [ ] 加载失败时展示什么，能不能重试
- [ ] 无权限时展示什么
- [ ] 网络异常时的处理
- [ ] 数据超长时的截断/换行规则

## 2. 交付前自检 Checklist

提交 PR / 交给别人 Review 之前，自己先过一遍：

### 视觉一致性
- [ ] 颜色全部来自 Token，没有硬编码 hex
- [ ] 间距都是 2 的倍数，优先用 `--space-*`
- [ ] 状态标签颜色用对了（查铁律第 2 条）
- [ ] 没有业务类型用彩色标签的情况（查铁律第 1 条）
- [ ] 主按钮只有一个，是蓝色（查铁律第 3 条）
- [ ] 卡片圆角 16px，列表行 44px，按钮 lg=48px

### 功能完整性
- [ ] 所有状态都有 UI 表现（不是只做了"正常态"）
- [ ] 表单提交中按钮禁用 + Loading
- [ ] 提交失败保留用户输入
- [ ] 空状态有对应组件
- [ ] 加载失败有重试入口

### 小程序适配
- [ ] 自定义导航栏适配了状态栏
- [ ] 标题没被胶囊按钮挡住
- [ ] Tab 页底部留了 TabBar 高度
- [ ] 底部固定按钮适配了安全区
- [ ] 可点击元素热区 ≥ 44×44px

### 代码质量
- [ ] WXSS 没有超过 3 层的嵌套
- [ ] 没有 `!important`
- [ ] 类名用 kebab-case
- [ ] 没有废弃代码和注释掉的大段代码

## 3. Review 标准

别人 Review 你的代码时，按以下优先级打回：

### P0（阻断合并）
- 导致核心任务无法完成、内容遮挡或不可操作
- 状态颜色映射错误
- 缺少关键状态（提交中 / 失败 / 空状态）
- 小程序适配问题（遮挡胶囊、不安全区）

### P1（必须在本轮修正，明显影响体验或一致性）
- 违反与当前场景适用的设计铁律
- 间距/圆角/字号不统一
- 交互细节不符合规范
- 字段命名不统一、可读性差
- 缺少状态枚举表或字段映射表

### P2（可选优化）
- 代码结构可以更清晰
- 可以抽成通用组件但没抽
- 动画/过渡可以更细腻

## 4. 交付信息放哪？

- 当前任务的状态表、字段映射、交互说明和 `NOT RUN` 优先写入 PR 回传或本人 `CURRENT` 文件要求的回传格式，不为每个页面新增 README。
- 只有需要长期维护、被多个任务复用的模块契约，才在模块已有文档入口中更新；不得新建平行台账或按日期无限追加交接。
- 通用规则或跨模块约定更新当前设计规范，并走 `CONTRIBUTING.md` 的贡献流程。

---

## 5. 交接给下一个人时

如果一个功能你做了一半要交接，必须保证：

1. 代码提交到了分支，有清晰的 commit message
2. 已完成的部分符合上面的交付标准
3. 未完成的部分列了 TODO，明确写到了哪一步
4. 跟后端对接过的字段/状态，写在了文档里
5. 有不确定的设计决策，标注了"待确认"并说明原因

> 交接不是"代码扔过去"，而是"下一个人接手就能继续干，不需要重新猜"。

## 1. 领域使命

让巡检从计划编制到现场闭环可执行、可追溯、不过度增加一线负担：计划明确，资源可用，到站可信，检查项和影像完整，审核与整改各有独立状态，历史档案能够复核。

B 对本领域承担产品、后端、Web、小程序、数据、测试和后续路线责任，不只负责巡检页面。

## 2. 核心链路

`检查项模板 → 计划编制/路线与资源 → 审批 → 执行包 → 出发准备 → 到站 → 检查与影像 → 提交 → 审核 → 整改包 → 完成与档案`

直接用户包括计划人员、现场运维人员和审核人员。完成标准必须覆盖无计划、资源不足、位置失败、弱网、重复提交、退回整改和历史查看。

## 3. 代码与验证地图

- 后端：`平台开发/backend/app.py` 中 `/api/inspection-v2/*`、巡检附件、审核及计划资源关联。
- Web：`平台开发/react-vite/src/pages/plan-schedules/`、`inspection-settings/`、`audit/`、`archive/`。
- 小程序：`pages/plan/`、`plan-detail/`、`plan-edit/`、`inspection/`、`review/`。
- 重点测试：计划检查项、现场执行、到站、出发资源、证据审核、整改和计划状态相关测试。

开始新事项前必须从计划配置追踪至现场结果和审核档案，不能只验证某个表单能提交。

## 4. 不可变规则

- 审批、现场执行、资源、证据审核和整改状态分轴保存，不能互相推断。
- 当前计划主链路是 `plan-schedules`；旧周计划只作兼容，不得重新作为权威来源。
- 周检默认，月检和季检按需组合成同一计划；检查项和照片要求由权威模板提供。
- 到站、签到、提交、审核和整改必须由服务端重读权限、位置、状态和版本。
- 影像归属业务对象；无可信来源或无归属材料不计有效证据。
- 整改创建独立整改包，不复活旧车辆、签到、申请或已完成执行包。
- 保存失败必须保留输入，弱网重试使用稳定幂等键。

## 5. 上下游协作

- A 提供站点档案、位置和可用范围；B 负责其在计划、路线和签到中的使用语义。
- C 提供车辆、备件、试剂及异常/工单资源契约；B 负责计划和现场如何申请、占用和归还。
- 主线提供人员权限、审批/消息公共能力和首页入口。
- 跨域功能由最终巡检结果所属负责人完成接线，资源负责人 Review 资源契约。

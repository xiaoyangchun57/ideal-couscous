## 1. 领域使命

让异常发现后能形成明确处置，并保证车辆、设备、物资、备件和试剂在真实业务中可申请、可占用、可维护、可追溯。用户不需要理解内部技术状态，但必须知道现在发生了什么、谁负责、下一步能做什么。

C 对本领域承担产品、后端、Web、小程序、数据、测试和后续路线责任，不只负责资源接口。

## 2. 核心链路

- 异常链：`监测异常/人工上报 → 告警 → 确认或转工单 → 派发/处置 → 核验 → 闭环追溯`
- 资源链：`档案与库存 → 可用性判断 → 申请/审批 → 占用或领用 → 使用记录 → 归还/维护/审计`
- 试剂链：`库存与有效期/QC → 关注项 → 更换或标定 → 状态恢复与记录`

直接用户包括现场运维、审核人员、资源管理员和系统管理员。

## 3. 代码与验证地图

- 后端：`平台开发/backend/app.py` 中 `/api/alerts*`、`/api/workorders*`、车辆、设备、物资、备件、试剂及操作日志端点。
- Web：`alerts/`、`workorders/`、`vehicles/`、`equipment/`、`reagents/`。
- 小程序：`pages/alert/`、`workorder/`、`vehicle/`、`reports/`，以及站点页中的试剂模式。
- 重点测试：告警工单接线、人工上报、车辆申请/履约、库存和试剂权限、状态迁移、幂等及失败回滚测试。

开始新事项前应核对资源的创建、占用、使用、归还和历史，而不是只检查列表显示。

## 4. 不可变规则

- 告警事实、工单处置和巡检异常相互关联但状态独立，不能用一个状态覆盖另一条链。
- 服务端是角色、站点范围、资源可用性、状态迁移和有效数量的最终权威。
- 车辆从批准到归还视为占用；未来不重叠排程可以选择，前序延期时必须提醒受影响排程。
- 车辆可用性由证照、年检、维护、故障和当前占用共同决定，不由单一字段推断。
- 备件在实际领用时扣减，审批不能假定库存仍可用。
- 试剂数量 `0`、单位、有效期、低余量和 QC 状态均是业务事实，不得因展示方便丢失。
- 库存、车辆履约、工单和审计记录不得静默物理删除；任何允许的清理必须按项目删除规则执行。

## 5. 上下游协作

- A 提供站点和有效监测事实；C 负责告警、工单和处置语义。

- 主线提供人员权限、审批/消息公共能力和审计治理。

- 维护异常和资源问题池，关注“状态看得懂、资源选得到、动作做得成、失败可恢复”。
- 完成当前事项后跑通告警到工单、车辆完整履约和至少一种库存/试剂维护链路。
- 主动提出三个有证据的后续候选并自行维护优先级。
- 本域低风险事项可自行启动；新权限、破坏性删除、公共审批/消息和跨域状态先冻结契约。

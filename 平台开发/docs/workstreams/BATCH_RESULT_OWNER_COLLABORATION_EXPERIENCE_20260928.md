# 批次结果负责人协作模式：经验吸收

> 日期：2026-09-28
>
> 性质：共享协作经验与执行参考，不是具体批次的开发授权、产品断点或发布许可
> 适用：同一用户结果由一人或多人、一个或多个领域共同完成的开发和优化任务

## 1. 为什么调整

此前容易把开发者自检、四眼检查、领域 Review、结果负责人 Review、主产品 Review 和真实 UI 验收全部设置为正式门禁。对于当前团队和代码体量，这会产生三个问题：

- 同一个简单问题被多次重复理解和验证，等待时间大于实施时间。
- 子 PR 分别向主产品排队，主产品只能看到多个半成品，无法高效判断最终用户结果。
- 多人从不同旧基线修改同一链路，最后才发现文件回退、契约不一致和汇总冲突。

本项目改为“入口一次拆清、结果负责人统一汇总、主产品一次完整 Review、真实 UI 一次验收”。减少的是重复审批，不是产品判断、自动测试、数据安全或发布门禁。

## 2. 默认闭环

```text
问题进入
→ 主产品一次拆解并冻结批次合同
→ 开发者实施、自检和定向测试
→ 结果负责人汇总、接线和形成完整候选
→ 主产品一次完整 Review
→ 合入 integration
→ 一次真实 UI 验收
→ 通过后才具备冻结候选资格
```

开发者自检、自动测试、结果负责人确认“可交主线”属于交付准备，不单独记为正式 Review。默认只有两道最终质量关口：

1. 主产品对完整批次候选的代码、产品和上下游 Review。
2. 独立真实 UI 对当前运行环境和用户结果的验收。

真实 UI 返修后只复核失败项及直接相邻区域；没有范围变化时，不重新启动整批 Review。

## 3. 收到问题时先形成批次合同

主产品先判断问题是单领域小改，还是需要多人协作的完整结果。单领域小改可以直接委派；多人协作只建立一份精简、自包含的批次执行合同，不为每个小问题重复建文件。

批次合同至少包含：

| 项目 | 必须明确的内容 |
|---|---|
| 用户结果 | 用户在哪个场景受阻，最终达到什么结果才算完成 |
| 结果负责人 | 唯一一人，对最终可用结果和汇总负责 |
| 产品规则 | 已冻结的流程、权限、状态、数据和不可变边界 |
| 子任务 | 每位参与者的交付结果，不只写“前端/后端” |
| 写入范围 | 允许文件、禁止文件、共享文件的串行写入窗口 |
| 输入输出契约 | 接口、字段、状态、错误、幂等、兼容和 Mock/样例 |
| 依赖与顺序 | 谁先做、谁消费、完成后通知谁、如何接线 |
| 分支与 PR | 批次分支、子任务目标分支和最终 PR 方向 |
| 验证 | 定向自动测试、组合测试和真实 UI 验收范围 |
| 停点 | 何时交主产品 Review，哪些变化必须暂停并升级 |

合同只保留当前仍有效的目标、范围、契约、验收和停点。已完成步骤和讨论过程不无限追加。

## 4. 责任划分方法

### 4.1 先按结果划分，再按文件划分

结果负责人按最终用户结果确定，不按谁修改的文件最多确定。文件范围用于防止并发写入，不能替代业务责任。

例如“站点 Tab 第二轮收口”是一个结果，可以包含站点主数据、监测查询、Web 消费和小程序试剂维护。即使子项跨 A、B、C，最终仍只有一名结果负责人。

### 4.2 一个文件同时只有一个活动写入者

- 同一批次、同一文件不得由两人并发修改。
- `backend/app.py` 等共享文件必须在批次合同中约定串行窗口和接棒顺序。
- 需要新增公共字段或改变公共契约时，先通知结果负责人，不先写两套实现再合并。
- 协作者发现范围外问题可以记录候选，不顺手扩大当前 PR。

### 4.3 产品变化与实现选择分开

既定规则内的代码结构、局部算法、测试补充和兼容实现由执行者与结果负责人决定。新增流程、状态、角色能力、公共导航、权限边界、审计规则或不可逆动作必须回主产品裁决。

## 5. 分支和合并模型

### 单人或单一写入者批次

```text
integration
└─ collab/<domain>-<task>
   └─ 最终 PR → integration
```

执行者完成实现和测试后，直接形成一个完整候选交主产品 Review。

### 多人协作批次

```text
integration
└─ batch/<result-id>                 结果负责人维护
   ├─ task/<provider-a>              子项负责人
   ├─ task/<provider-b>              子项负责人
   └─ task/<provider-c>              子项负责人

task/* → batch/*                     由结果负责人接收和解决冲突
batch/* → integration                只提交一个最终批次 PR 给主产品
```

规则：

1. 批次分支从最新 `origin/integration` 创建。
2. 子任务分支以批次约定基线创建，子 PR 默认进入 `batch/*`，不分别向 `integration` 排队。
3. 结果负责人决定接入顺序、处理共享文件冲突并运行组合测试。
4. 主产品只 Review `batch/* → integration` 的最终完整候选。
5. 合入 `integration` 后进行真实 UI 验收；`integration` 不是生产事实，也不自动获得冻结或部署资格。
6. 发现旧分支会回退当前基线时，从最新批次基线重放有效增量，不以“Git 可自动合并”代替业务兼容判断。

## 6. Review 口径

### 不再作为独立门禁的动作

- 作者阅读自己的差异和运行定向测试。
- 结果负责人确认子项齐全、契约已接通、证据可交主线。
- 受影响领域对字段、接口或数据语义提供咨询意见。
- 设计师 Agent 核对实现是否偏离已交付设计基线。

这些动作仍然要做，但属于实施和汇总责任，不分别产生“等待 Review”的流程状态。

### 主产品完整 Review

“完整”指覆盖本批用户链路和直接上下游，不是每次重审全仓库。至少判断：

- 用户目标是否闭环，是否出现多份半成品拼接。
- 范围、权限、状态、数据和错误语义是否符合冻结规则。
- 子项接线、兼容和直接相邻回归是否完整。
- 是否存在越权、部分写入、不可逆或历史数据回退风险。
- 自动测试与风险是否相称，真实 UI 验收条件是否准备好。

### 真实 UI 验收

真实 UI 只验当前完整候选的真实表现，包括布局、滚动、输入、弹层、导航、角色差异、失败恢复和跨页面结果。自动测试、接口调用、静态截图和设计稿不能替代真实 UI PASS。

### GitHub 形式审批

仓库要求的非作者审批可以由结果负责人、协作者或主产品完成。若 PR 由主产品自己提交，需要一名未参与提交者做文档或代码一致性形式审批。该审批不拥有产品否决权，也不自动构成额外产品 Review。

## 7. 各角色如何执行

### 主产品

- 在入口一次定义用户结果、产品规则、结果负责人、子任务边界和最终验收。
- 只接收改变产品规则、跨域冲突、高风险动作和最终完整候选。
- 不逐个审批简单子 PR，不充当 A/B/C 的技术消息中转。
- 对最终候选做一次完整 Review，并对真实 UI 证据作最终裁决。

### 结果负责人

- 维护唯一批次合同和 `batch/*` 分支，对最终用户结果负责。
- 拆分子项、冻结契约、安排共享文件写入顺序并主动通知下一行动人。
- 接收子 PR、解决冲突、完成接线和组合测试。
- 不把多个未汇总子项分别交主产品 Review；形成一个完整候选后一次回传。
- 既定规则内可自主裁决实现问题；产品范围改变时立即停下并升级。

### 子项负责人或领域提供方

- 只执行合同内的交付结果和文件范围，完成自检、定向测试和清晰回传。
- 对自己提供的接口、字段、状态、兼容和失败语义负责。
- PR 进入结果负责人的批次分支；不绕过结果负责人直接请求主产品逐项审批。
- 发现契约不成立或需要扩大范围时，先通知结果负责人。

### 开发经理

- 是当前交接授权范围内的唯一业务代码写入者。
- 修改前核对代码、调用方、测试和现有差异；不回退他人改动。
- 保证失败可见、可重试、无部分副作用，并提供风险相称的自动证据。
- 开发完成即停止扩大范围，把可复核候选交结果负责人汇总。

### 各领域设计师 Agent

- 在结构、信息层级、卡片、筛选、弹层或图标发生变化时提供静态设计基线。
- 对本领域设计方案负责，不改变权限、接口、状态和数据规则。
- 未经明确授权不与开发经理并发写同一 UI 文件。
- 设计复核属于交付准备；最终运行效果仍由独立真实 UI 验收裁决。

### 独立真实 UI 验收

- 使用当前 `integration` 候选和隔离数据复现真实用户路径。
- 只报告可复现问题、证据、影响范围和验收结论，不代开发改代码。
- 返修后复验失败项及直接相邻区域，避免无范围变化的整轮重验。

### GitHub Reviewer

- 满足非作者审批和仓库门禁，核对范围、明显回退、测试证据和文档一致性。
- 不替代结果负责人，不重开已冻结产品规则，不拥有产品否决权。

### 独立发布任务

- 只接收已冻结、不可变的候选；负责生产预检、备份、部署、回滚验证和发布证据。
- 不参与开发批次的产品拆解，也不因 `integration` 或真实 UI PASS 自动取得部署授权。

## 8. 需要额外风险证据的事项

以下事项不机械增加一轮人员 Review，但必须提高证据强度：

- 权限、认证、数据范围和服务端状态迁移。
- 批量迁移、站点退役、物理删除和历史数据修正。
- 库存、车辆履约、审计和其他不可逆业务记录。
- 公共接口、公共数据模型、导航和共享组件。
- 生产配置、服务器操作、冻结和部署。

优先采用成功/越权/不存在/状态冲突/重复请求/失败回滚测试、预览指纹、备份、事务和回滚证据加强，而不是让多人重复做相同产品 Review。

## 9. 升级条件

出现下列任一情况，结果负责人暂停汇总并交主产品裁决：

- 原用户目标不能按当前方案闭环。
- 需要新增或删除流程、页面入口、状态或角色能力。
- 需要改变公共接口、权限、审计或不可逆数据规则。
- 两个领域对契约、业务归属或优先级无法达成一致。
- 实际改动明显超出批次合同，或同一文件出现并发写入。

普通实现选择、局部布局接线、测试补充、分支同步和可自行解决的代码冲突不升级到主产品。

## 10. 站点 Tab 第二轮示例

统一用户结果是“站点目录、监测数据、试剂状态和维护操作在小程序中形成完整可验收链路”，而不是三个相互独立的 PR。

- A 是结果负责人，维护批次分支和最终候选。
- 站点主数据刷新、Web 消费和试剂接口可以由不同参与者完成，但子 PR 先进入 A 的批次分支。
- A 负责使用最新 `integration` 接线，避免旧分支回退现有试剂契约、小程序和协作治理文件。
- 主产品不分别 Review 每个简单子项，只 Review A 汇总后的完整候选。
- 完整候选进入 `integration` 后，独立真实 UI 验收站点/试剂切换、筛选、卡片、弹层、TabBar、失败重试和角色范围。

## 11. 常见错误

- 把每个子 PR 都标记为“待主产品 Review”。
- 结果负责人只负责转发消息，不负责最终接线。
- 按前端、后端或文件数量决定结果负责人。
- 多人从不同旧基线修改同一链路，最后才处理回退。
- 把自动测试、设计静态检查或开发者浏览器观察冒充真实 UI PASS。
- UI 返修后无范围变化仍重新启动全量 Review。
- 为了满足形式审批，让协作者重新裁决已经冻结的产品规则。

本经验的核心不是取消质量控制，而是把质量控制集中在正确位置：入口拆清、实现自证、结果负责人汇总、主产品一次完整 Review、真实 UI 一次验收。

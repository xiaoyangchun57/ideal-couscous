# 专业视觉设计师协作规范

本文件适用于 `平台开发/miniprogram/` 下由专业视觉设计师承担的前端实现。它补充仓库根 `AGENTS.md`，不替代产品契约、业务规则或用户当次授权。用户当次明确要求优先。

目标是让设计师能够直接落实视觉，同时保证页面仍连接原有业务。视觉实现可以重构外观和布局，但不得在不说明的情况下改变数据、状态、事件或流程。

## 一、开始条件

1. 开始前读取仓库根 `AGENTS.md`、当前产品断点，以及本次指定的页面母版和设计系统。
2. 视觉权威依次为：
   - 本次明确指定的页面母版；
   - `water-om-apple-hig/water-om-apple-hig.design` 与对应 `pages/*.html`；
   - `.design_library/水质运维-Apple/` 的 Token、组件规格和页面模板；
   - `water-om-apple-hig/DESIGN_HANDOFF.md` 的微信小程序适配规则。
3. 修改前列出本轮文件白名单，并核对这些文件的当前差异和最后修改时间。发现开发经理、其他任务或外部工具正在写同一文件，立即停止，不覆盖、不猜测合并。
4. 没有明确母版的场景，先用设计系统的标准页面模板和现有组件补设计；不得直接在真实代码中发明另一套视觉语言。

## 二、设计师可以决定的内容

在本次文件白名单内，设计师可以决定：

- 信息层级、留白、对齐、尺寸、字体层级、颜色映射、圆角、阴影和分隔方式。
- 现有业务区块的视觉排序、组合与响应式布局。
- 使用现有 Token 和组件实现页面、卡片、列表、表单、弹层、空态、反馈和安全区适配。
- 为满足 44x44px 最小触达面积增加不改变业务语义的点击外层。
- 对 WXML 做纯展示容器调整、class 增删和视觉资源替换。

所有类型/分类标签使用中性灰；只有真实状态使用语义色。已有 Token 或组件能表达时不得硬编码新颜色、间距、字号、圆角或私有变体。

设计决策必须以实际渲染结果为准，不能仅凭代码逻辑推断视觉效果。修改前要在脑中过一遍所有状态（加载、空态、错误、禁用、长内容、短内容等）的真实表现，不能只看正常数据路径；因忽略某状态导致的界面崩坏视为设计缺陷，不是代码问题。

## 三、未经逐项授权禁止修改

以下内容属于业务契约，不属于视觉设计自由度：

1. 不修改 `.js`、服务层、工具函数、后端、数据库、接口、测试数据、路由表或权限判断。
2. 不新增、删除、改名或改写任何数据字段、字段映射、接口参数、响应解析、状态枚举和默认值。
3. 不修改 WXML 中的：
   - `{{...}}` 数据绑定表达式；
   - `wx:if`、`wx:elif`、`wx:else`、`wx:for`、`wx:key`；
   - `bindtap`、`catchtap`、`bindinput`、`bindchange` 等事件；
   - `data-*`、组件属性、`disabled`、`loading` 和表单值绑定；
   - 页面 URL、跳转目标、查询参数和返回路径。
4. 不改变按钮、标签、错误提示和状态文案所表达的业务含义；微文案优化需要产品明确授权。
5. 不用静态样例、假数据或本地推断替代真实字段；不因视觉稿缺少某状态而删除该状态。
6. 不为适配视觉新增业务页面、步骤、权限、审批、状态或平行入口。
7. 不修改或放宽既有测试来迁就新布局。测试暴露契约冲突时先停手并提交冲突说明。

即使设计师具备代码修改能力，也不自动获得上述权限。需要改动时，先提交“契约变更请求”，由产品确认并交开发经理接线。

## 四、母版继承要求

1. 每个页面开工前指定一个页面级母版；完成后必须与该母版并排检查，不凭代码或记忆判断风格一致。
2. 保留母版的视觉骨架：页面背景、导航结构、内容宽度、卡片语言、排版层级、间距节奏、动作区和反馈样式。
3. 新场景优先组合设计系统现有组件。确实缺少组件时，先在设计系统中补充“何时用、何时不用、状态和尺寸”，经确认后再落到页面。
4. 任何有意偏离母版的地方必须在动手前列出：偏离位置、原因、替代方案和影响页面；未获确认不得静默偏离。
5. 微信原生导航、胶囊、TabBar 和安全区按运行时边界适配。二级/三级页默认使用微信原生导航，不额外叠加业务页头。

## 五、视觉与业务分层

真实页面融合遵循以下顺序：

1. 产品提供页面骨架：路由、模块责任、真实字段、状态、事件、失败分支和不变量。
2. 设计师基于母版决定布局、组件组合和视觉表达。
3. 设计师只落地视觉白名单；开发经理负责事件、接口、数据绑定、状态机和失败保护。
4. 设计师交接后，开发经理只做契约 Review 和必要接线，不重新设计视觉。

如果视觉目标需要改变现有绑定或流程，设计师不得自行“顺手修正”。回传以下四项后停手：视觉目标、当前业务限制、所需契约变化、可用的纯视觉替代方案。

## 六、写入纪律

1. 同一文件同一时间只能有一个写入者。开始写入前取得明确授权，完成后立即释放。
2. 只修改白名单文件；不得顺手格式化、重命名、整理或覆盖其他已有改动。
3. 发现文件在本轮期间发生无法辨认的变化，立即停止并报告，不重放补丁、不恢复旧版本。
4. 每次保存后核对实际差异。若 diff 中出现数据绑定、事件、路由、字段或状态判断变化，视为越界，停止并等待产品处理。
5. 未经要求不提交、不暂存、不发布、不操作真实业务数据。

## 七、完成验证

设计师交付前必须同时满足：

- 在真实微信小程序中检查，不以 HTML 原型、静态截图或代码预览代替最终判断。
- 至少覆盖 375x812 和 360x800 等效视口，并按真实胶囊边界检查页头。
- 与指定母版并排检查视觉骨架、Token、组件、间距、排版、状态色和安全区。
- 所有主要按钮、列表项、输入、弹层和返回入口可点击，无遮挡、无不可见命中层、无横向溢出。
- 加载、空态、长内容、失败、禁用、提交中和权限差异等本次相关状态均未因新布局消失。
- WXML 可编译；原有直接测试和事件/路由契约检查通过。
- 对视觉任务做绑定差异复核：事件名、`data-*`、条件、循环、字段表达式和路由在修改前后保持一致。

自动测试通过不等于视觉通过；截图好看也不等于业务连接正确。两类证据必须分别成立。

## 八、回传格式

日常回传只写四项：

1. 做了什么视觉调整。
2. 为什么这样调整，继承了哪个母版或组件。
3. 真实页面结果与验证状态。
4. 是否存在需要产品拍板的母版偏离或契约变更。

必须附实际修改文件清单。没有明确写出的字段、绑定、事件、路由和业务状态，默认均未修改。
